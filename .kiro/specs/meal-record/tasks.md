## 補足

### 並列実行について

`(P)` を付けたのは 1.2 と 1.3 の 2 つのみ。食事区分の推定とノートの生成は責務の境界が重ならず、
触れるファイルも異なるため同時に進められる。どちらも 1.1 が定義する語彙に依存するため、
`_Depends: 1.1_` を明示している。

以下は並列にできない。

- **1.1 と 1.2 / 1.3** — 1.1 が記録に使う語彙を定義する。これが無いと他の実装が始められない
- **4.1 / 4.2 / 4.3** — いずれも同じ記録画面を触る。同じファイルを奪い合う
- **3.1** — 1.1〜1.3 と 2.1 のすべてに依存する。配線であるため、繋ぐ先が揃っていないと成立しない

### 実測は設計の段階で終わっている

本 spec が依存する外部 API の挙動は、設計を書き終えた時点で実測済みである。

| 確かめたこと | 結果 |
|---|---|
| 識別子を送らない新規作成 | 201 で成功する |
| 同じ名前で 2 回目の書き込み | **422**。重複の判定に使う |
| 最小権限のトークンで足りるか | 足りる |
| 日本語の往復 | 壊れない |

したがって**実装の途中で前提が崩れる余地は小さい**。崩れた場合は設計書の
Revalidation Triggers に従い、報告して人の判断を仰ぐ。

### 実装中に見つかった別タスクの候補

- **`parseNumber` と `MEAL_KINDS` の共通化** — `actions.ts` と `record-form.tsx` の二重定義を `src/lib/` へ切り出す。条件のずれを構造的に防ぐ。区分の読み取り（`readKind` / `parseMealKind`）も同型なので併せて切り出す。design.md の File Structure Plan の更新を含む
- **`layout.tsx` の `lang="en"`** — 画面の文面は日本語なので `ja` が正しい。各タスクの boundary 外のため触っていない
- **`quote()` が C0 制御文字を素通りする** — `src/lib/note.ts` の `quote()` は `\` と `"` と
  改行をエスケープするが、生の制御文字（`\u0001`〜`\u0008`, `\u000b`, `\u000c`,
  `\u000e`〜`\u001f`）はそのまま通す。`foods: ["a\u0001b"]` は js-yaml が
  `expected valid JSON character` で throw し、**そのノートの frontmatter 全体が
  読めなくなる**（`,` が混ざった場合より被害が大きい）。ただし到達経路は**フォームを
  介さない POST のみ**で、`<input type="text">` からは入力できない。対処は
  `\r` / `\n` の置換の前に 1 行足すだけで済む
- **`unauthorized` 分岐のテストを `actions.test.ts` に加える** — 現在の 6 件はすべて入力不正の確認で、**認証の再検証（多層防御の 2 層目）を守るテストが 1 件もない**。`app-foundation` の design.md が「`matcher` の変更や Server Function を別ルートへ移すリファクタによって保護が静かに外れうる」と警告しており、2 層目はその備えである。テストが無いと、2 層目が壊れても遮断点が効いている間は誰も気づかない。`next/headers` を `vi.mock` し、資格情報が設定済みで「ヘッダなし」「値が不一致」のときに `unauthorized` を返し**書き込みを試みない**ことを確認する。対照として「一致すれば書き込む」も置く
- **成功時に入力をクリアする** — 4.3 でリセットを捨てたため、記録に成功しても食材・時刻・区分・料理名が残る。次の 1 食を記録するときに手で消す必要がある
- **入力の修正でエラー文面を消す** — `record-form.tsx` の `draftError` は次に「加える」が成功したときだけ消える。欄を直している間も文面が残る

### 本 spec に含めないもの

要件と設計の合意に従い、以下はタスク化していない。

- **栄養価の推定** — 食材名から 100g あたりの値を出す仕組み。次の spec で扱う。
  本 spec の「1 食材につき 4 項目を打つ」手間はこれで解消する見込み
- **プリセット** — よく食べるものを貯めて選べるようにする。何を貯めるべきかは
  手入力の記録が溜まってから決める
- 献立単位の記録、写真からの推定
- 集計とサマリーの更新 — Obsidian の Bases と Dataview が担う
- 記録した内容の一覧表示と検索
- 公開環境への配置作業

## Implementation Notes

- **1.1**: 新規ファイルを追加するタスクでは、RED フェーズの証拠が「import を解決できない」というエラーになる。アサーション単位の RED にはならないため、**テストが振る舞いを識別することは突然変異テストで裏づける**（実装を壊してテストが落ちるかを確かめ、確認後に復元する）
- **5.1**: Obsidian の Bases での一覧表示だけが**利用者の環境でしか確認できない**。他の 3 項目（送信の成功・frontmatter 8 項目・重複）は実機で確認済み。この 1 項目のため 5.1 は未完了のまま
- **5.1 / 5.2**: 実機で確認した。vault の実ファイルは frontmatter 8 項目が design の順序で揃い、**本文に並べた数値の和が frontmatter の合計に一致**した（`468+283=751` / `8+48=56`）。画面の数字とも一致。`menu` に量あり・`foods` に量なしの作り分けも成立
- **5.1 / 5.2**: 設定不足の確認は**まだ使っていない時刻**で行う。重複する時刻だと「書き込みを試みたが重複で失敗した」のか「試みずに止まった」のかが区別できない（受入基準 6.3 は試みないことを求めている）
- **5.2**: **遮断点の 401 は GET と POST の両方で確認する。** Server Action は記録画面への POST として扱われるため、GET だけ確認しても送信経路が守られている証拠にならない
- **5.2**: 多層防御の 2 層目（Server Action 内の再検証）を**HTTP 経由で実走させることはできない**。遮断点が先に 401 を返すため 2 層目に到達しない。`src/proxy.ts` の `matcher` を一時的に緩める方法は**権限の仕組みが「Security Weaken」として拒否する**（正しい挙動。迂回しないこと）。`recordMeal` を直接呼ぶテストで確認する
- **5.2**: 2 層目の確認では**対照を置く**。「ヘッダなしで書き込み 0 回」だけでは装置が壊れている可能性と区別できない。「ヘッダが一致すれば 1 回」を併せて確認する
- **4.3**: **`<form action={formAction}>` を使わない。** `action` に関数を渡すと React が送信のあと `form.reset()` を呼び、`<select>` が `value` で制御されていても先頭の選択肢に戻ったまま復元されない（再描画は起きるが `value` が同値なので DOM に書き直されない）。**表示と送られる値が食い違い、やり直すと利用者が選んでいない区分で記録される。** `onSubmit` で `FormData` を組んで `startTransition` の中で `formAction` を呼ぶ。すべての入力を制御下に置く方式でも解決しない（実測で確認）
- **4.3**: この挙動は**テストで押さえてある**。`action={formAction}` に戻すと入力保持のテストが落ちる。design どおりに直すリファクタで受入基準 5.4 が静かに壊れるのを防ぐため
- **4.3**: 成功後も入力が残る（リセットを捨てた副作用）。誤記録にはならない（同じ内容を再送すると同名ファイルで重複になる）が、次の 1 食を記録するときに前の食材を手で消す手数が残る。**「成功時に入力をクリアする」を別タスクの候補に挙げる**
- **4.2**: **日時の 0 埋めはテストで押さえる。** `padStart(2, "0")` を外しても、月・日・時・分がすべて 2 桁の時刻（`16:30` など）でテストしていると全件通ってしまう。0 埋めが壊れると `2026-1-5T9:05` が送られて受付の正規表現に一致せず、**1〜9 月・1〜9 日・0〜9 時・0〜9 分の食事だけが理由の分からない入力不正になる**（利用者の朝食は 9:30 ごろ）。**1 桁になる時刻でテストすること**
- **4.2**: 現在時刻は `useEffect(..., [])` の中で決める。`useState` の遅延初期化だとレンダリング中に評価されるため**サーバー（UTC）とクライアント（ローカル）で値が食い違い hydration mismatch になる**。初回レンダリングは空欄・既定の区分にしておき、hydration 後に effect で埋める
- **4.2**: 時刻欄が空のときは区分を**直前の値のまま保つ**。既定値へ戻すと利用者が選んだ区分を壊すため（受入基準 3.4 に反する）。送信時はサーバーが形式不一致で弾く
- **4.2**: `MEAL_KINDS` と区分の読み取り（`readKind` / `parseMealKind`）が `actions.ts` と `record-form.tsx` で二重定義。内容はバイト単位で一致しているが、**ずれると「画面の選択肢にあるのにサーバーが入力不正を返す」という、利用者に理由がまったく分からない失敗になる**。`parseNumber` より危険度が高い。共通化の別タスクに含める
- **4.3 への申し送り**: 送信ボタンの無効化条件に **`eatenAt === ""`（時刻が空でない）を含めること**。design.md の記録フォームの Validation の列挙は「食材が 0 件 / 数値が不正 / 名前が空」で**時刻が抜けている**。入れないと、時刻欄を空にしたまま送信した利用者が「入力不正」という理由だけを見せられ、どの欄が悪いか分からない（`RecordState` の `invalid` は欄を区別しない）
- **4.1**: 下書き行（これから加える 1 件）の入力欄に `name` 属性を付けないこと。**この落とし穴はテストで押さえる** — 下書きの値が `FormData` に混ざらないことを確かめるテストを置き、付けてみると落ちることを確認した
- **4.1**: 受入基準 1.6（対象が 0 件なら送信を受け付けない）は、4.1 の時点では送信コントロールが無いため空振りで成立している。**4.3 で送信ボタンの無効化を必ず実装すること**
- **4.1**: `parseNumber` が `src/app/actions.ts` と `src/app/record-form.tsx` に**二重定義されている**。現時点で条件は完全一致（`trim` → 空文字を null → `Number()` → `Number.isFinite`）だが、**ずれを検知する手段がない**。片方だけ直すと「画面で通ってサーバーで弾かれる」が起き、利用者には理由が分からない。`src/lib/` への切り出しを別タスクとして切る（design.md の File Structure Plan の更新を含む）
- **4.1**: 数値欄を `type="number"` にすると、不正な文字列（`abc` / `e` / `-` のみ / ペースト）は HTML の仕様で bad input 状態になり `input.value` が空文字を返す。つまり**画面側に届くのは空文字判定の経路**で、`NaN` 分岐には到達しにくい。利用者が実際に踏むのは空文字側なので、そこをテストで覆えば足りる
- **3.1**: 送信データの項目名は、食材ごとに `name` / `kcalPer100g` / `proteinPer100g` / `grams` を繰り返し、単一項目として `eatenAt` / `kind` / `dish` を送る形で確定した。**4.1 では「これから加える 1 件」の下書き行にこの項目名を付けないこと。** 付けると未入力のまま送信したときに配列に空の要素が増え、確定済みの食材が正しくても送信全体が入力不正になる
- **3.1**: **入力の検証を `headers()` の呼び出しより前に置く。** そうしないと入力検証のテストが書けない（`headers()` がランタイム外で例外を投げる）。機微な情報（`reason: "config"` = 配置環境の設定が揃っているか）は認証の検証より後ろにあるため、順序を入れ替える必要はない
- **3.1**: 4 つの繰り返し項目の**長さ一致検査がテストで覆われていない**（突然変異テストで検査を削除しても全テストが通る）。spec が要求する検証項目ではなく（design.md の Validation は「0 件 / 数値不正 / 名前が空」の 3 つ）、画面側は構造上 4 本組を同数で並べるため許容した。補強するなら `name` 1 件に対し `grams` を 2 件送るテストを 1 件足す
