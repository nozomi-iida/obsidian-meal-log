- [x] 1. 実測で設計の前提を潰す

`meal-record` では design を書き終えた時点で GitHub API を実際に叩き、「重複は 422（409 ではない）」を
確定させた。**実測しなければ「重複なのに権限エラーと表示する」実装になっていた。**

本 spec では `ANTHROPIC_API_KEY` が環境に無いため、この工程を design の段階で行えなかった。
**実装の最初に行う。**

## 補足

### ここで一旦止めた（2026-10-17）

**4.4 までで実用可能な状態になっている。** 利用者がベンチプレスを休んでいて食事管理の
必要性が下がったため、4.5 以降を残して区切った。トレーニングを再開したくなったら続ける。

**いま動くもの**（実機で確認済み）

```
食材名と量だけ入力  →  「推定する」  →  100g あたりの値と合計が出る
値を手で直せる      →  直した値は再推定で上書きされない
「記録する」        →  vault の Meals/items/YYYY-MM-DD-HHmm.md に frontmatter 8 項目で記録
```

**実測で分かっていること**（詳細は `research.md`）

| 確かめたこと | 結果 |
|---|---|
| 曖昧な名前（「肉」など） | 5 件 × 5 回すべて `null`。黙って平均値を返さない |
| たんぱく質の精度 | 8 件中 6 件が誤差 0% |
| エネルギーの精度 | **+4〜+9% 高めに出る**。七訂（2015 年版）相当の値が返るため |
| 速度 | 食材 4 件で 2.4 秒、30 件で 17 秒 |
| 費用 | 1 回 0.05 円。月 120 回で 6 円程度 |

**残っているもの**

- **4.5** 値が揃っていない食材を示す。無くても記録はできる。
  **`note` の有無で文面が 2 系統に分かれている**ので、一律の印を入れるときに揃える
- **5.1 / 5.2** 動作の確認。4.4 までの実装はブラウザで確認済みだが、
  spec の確認項目としては未記録
- **`meal-record` の 5.1** Obsidian の Bases での一覧表示。利用者の環境でしか確認できない

### 実測を先に置いた理由

`meal-record` では design を書き終えた時点で実測を済ませ、その結果（重複は 422）を design に
反映してから実装に入った。本 spec は `ANTHROPIC_API_KEY` が無いため同じ順序にできなかった。

**タスク 1.1 の結果によって design が変わりうる。** 曖昧な名前で `null` が返らない場合は、
プロンプトの作り直しか、別の仕掛け（候補を複数出させて食い違いを検知するなど）が必要になる。
**その判定を 1.1 の完了状態に入れてある。**

### 並列実行について

- **1.2 は 1.1 と並行して進められる**（どちらも実測で、互いの結果に依存しない）
- **4.1 は API キーを必要としない。** 画面から 100g あたりの入力欄を外す作業で、
  推定の配線は 4.2 以降である。1.x / 2.1 / 3.1 と並行して進められる
- それ以外は一直線に依存する。4.2 以降はすべて `record-form.tsx` を触るため同時に進めると衝突する

### 本 spec に含めないもの

- **推定した値の保存** — プリセットの spec が扱う。何を貯めるべきかは記録が溜まってから決める
- **外食・人が作ったものの記録** — 生で測れない。写真からの推定として後続の spec が扱う
- **食材名の正規化** — 入力された表記をそのまま記録に使う

`/kiro-steering` で拾う。

### `meal-record` から引き継ぐ知見

実装に入る前に `.kiro/specs/meal-record/tasks.md` の `## Implementation Notes` を読むこと。
とくに次の 5 件は本 spec でも同じ失敗が起きうる。

- **下書き行に項目名を付けない**（4.1）— 付けると送信全体が入力不正になる
- **日時の 0 埋めはテストで押さえる**（4.2）— 1 桁になる時刻でテストすること
- **`<form action={formAction}>` を使わない**（4.3）— React の自動リセットで `<select>` が壊れる
- **負の値と YAML の引用**（6.1）— 横断検証で見つかった。要件の文面に忠実な実装が意図から外れた例
- **`.env*` は Read / Write / Edit から触れない**（2.1）— `git diff` をファイル名なしで使う

## meal-record への申し送り（別タスクの候補）

3.1 の実装とレビューの過程で、`meal-record` の既存の抜けが 1 件見つかった。
**本 spec の境界の外なので触っていない。**

- **`recordMeal` が vault の失敗分類をそのまま返す経路がテストで覆われていない。**
  `src/app/actions.ts` の `reason: result.reason` を `"network"` に固定しても、
  テストが 87 件すべて通る（実装者とレビュアーが独立に確認）。
  **壊れると vault の重複・権限・通信のすべてが「通信エラー、時間を置いてやり直す」と
  表示され、利用者は直らない失敗を再送し続ける。** `meal-record` が GitHub API を実測して
  「重複は 422（409 ではない）」を確定させた労力が、1 行の変更で無効化されうる。
  描画側で覆われているのは `duplicate` / `permission` / `network` / `config` の 4 つで、
  抜けているのは受付の 1 行の受け渡しである。
  `writeNote` が `duplicate` / `permission` を返したときの分類を押さえるテストを 2 件足す
- **記録側の `ERROR_MESSAGES` の `unauthorized` と `invalid` の文面が 1 件もテストで
  覆われていない**（4.3 のレビューで実測）。`unauthorized` の文面から「遮断点」を
  落としても全件通る。推定側（`ESTIMATE_ERROR_MESSAGES`）は 6 分類すべてを
  `record-form.test.tsx` が押さえているので、**記録側だけが非対称に抜けている**。
  文面を押さえるテストを 2 件足す
- **`unauthorized` 分岐のテストを書く手段が判明した。** `vi.mock("next/headers", ...)` を
  `importOriginal` 併用の部分モックにし、**既定の実装を本物のまま残す**。これにより
  既存の「要求の外では例外になる」ことに依存したテストが壊れない。`afterEach` の
  `mockReset()` が必須である（削除すると shuffle の seed によって落ちる）。
  3.1 の `estimateFoods` でこの形を使っており、`recordMeal` にも同じ形で書ける

## Implementation Notes

- **3.1**: 処理の順序は **入力の検証 → 認証の再検証 → 資格情報 → 推定**。
  **認証より先に資格情報を見てはいけない。** 未認証の相手に「このサーバーは
  `ANTHROPIC_API_KEY` が設定されていない」という配置環境の情報を教えることになる。
  順序を入れ替えると落ちるテストを置いてある
- **3.1**: `recordMeal` の「認証 → 資格情報」の順序は、既存のテストが
  **偶発的に固定している**（`rejects.toThrow("outside a request scope")` が
  `headers()` への到達を主張するため、認証を後ろへ動かすと例外が出ずに落ちる）。
  意図して書かれたテストではないので、既存テストの書き換えで静かに失われうる
- **3.1**: `page.tsx` の `maxDuration` は **1.2 の実測で見直す**。現在は
  `estimate.ts` の `AbortSignal.timeout`（30 秒）の 2 倍という根拠で 60 秒。
  **`page.tsx` のコメントが `estimate.ts` の値を参照しているため、
  片方だけ変えると記述が静かに古くなる。** 1.2 では両方を揃えて見直すこと
- **3.1**: `parseFoodNames` と `parseFoodInputs` で名前の読み方（`trim()` → 空なら不正）が
  重複している。現在はバイト単位で一致。ずれると**推定では通る名前が記録で弾かれ、
  理由の分からない入力不正になる**。3 行・同一ファイル・隣接なので今は抽出しない。
  `name` の読み手が 3 つ目になった時点で `src/lib/` へ切り出す
- **4.1**: 「記録する」の無効化は 4 条件（`pending` / `entries.length === 0` /
  `eatenAt === ""` / `hasMissingValue`）だが、**4.1 の時点で突然変異テストが検知できるのは
  `hasMissingValue` と `entries.length === 0` の 2 条件だけである**。`per100g` を埋める経路が
  まだ無く `hasMissingValue` が常にボタンを無効にするため、他の条件の寄与が観測できない。
  14 件の突然変異で確認した
- **4.1**: 値を持たない食材も **4 項目すべてを並べ、値の無い 2 項目を空文字で出す**。
  項目を省くと `parseFoodInputs` の長さ一致検査が崩れ、別の食材の値が隣にずれて入る。
  `name` ごと省くと**その食材が記録から静かに抜ける**（誤った記録が「成功」として作られる）。
  空で出せば受付の `parseNumber` が空文字を `null` と判定し、`headers()` も vault も触る前に
  送信全体が入力不正になる。**「記録する」の無効化が壊れても値の無い記録が vault に書かれない**
- **4.2 / 4.3 への申し送り**: `per100g` を埋められるようになった時点で、次の 2 件の
  アサーションを**回復すること**。
  1. **時刻が空のとき「記録する」が押せない**こと。この条件は design.md の Validation の
     列挙に一度抜けており、`meal-record` の 4.2 のレビューの申し送りだけで救われた。
     記録を残さずに無検査のまま引き継ぐと、同じ失敗を繰り返す
  2. **送信中は押せず、重ねての送信が受付に届かない**こと。`submit()` に `pending` の
     ガードは無く、**二重送信を止めているのは `disabled` 属性だけ**である
- **4.1**: 合計の算出（`calculateItem` → `sumNutrition`）の画面側の経路は 4.1 では到達できない。
  どの食材も値を持てないため合計が常に 0 になる。純粋関数は `nutrition.test.ts` が担保しており、
  画面側は 4.3 で戻る
- **4.2**: 「推定する」は `type="button"` + `onClick` にする。`type="submit"` を 2 つ並べると
  押されたボタンを区別できず、推定に送る項目（値を持たない食材の名前だけ）はフォームの項目と
  一致しない。この結果、**HTML の暗黙の送信（Enter）の default button は「記録する」のままに
  なる**
- **4.2**: `estimateTargets`（`useRef<readonly number[]>`）で求めた順の id を控え、結果と位置で
  突き合わせる。**食材名で突き合わせると同名の食材 2 件で取り違える**（同名 2 件の結果が
  取り違わらないことをテストで押さえてある）。推定中に対象を取り消しても `indexOf` が元の
  並びの位置を返すためずれない。推定中に加えた食材は `-1` で対象外になる。
  **`nextId` は記録の成功後もリセットしないため id が再利用されず、古い
  `estimateTargets.current` が別の食材に当たらない**
- **4.2**: 「記録する」の無効化の `estimating` は、**推定中に値を持たない食材を取り消す**ことで
  分離できる。値の不足が無くなり、残る無効化の理由が推定中であることだけになる。
  4.1 の申し送りで観測できなかった 2 条件（`eatenAt === ""` / `pending`）も、推定で値が
  埋まるようになったため突然変異テストで検知できる
- **4.2**: 残った未検知は 2 つ。**どちらも突然変異を当てて全件が通ることを実測した。**
  1 つは `ok: false` のときの `note` の代入（`note` はまだ描画されない。**4.3 が描画する**）、
  もう 1 つは反映時の上書き防止ガード（`entry.per100g !== null || entry.edited` を外しても
  落ちない。推定中に値が決まる経路が `edited` の立つ 4.4 まで無い）。
  **4.3 / 4.4 で必ずテストで覆うこと**
- **4.2 / 4.3 への申し送り**: 推定の失敗（`EstimateState` の `error`）が画面に出ない。
  `describeProgress()` は `submitResult` しか見ない。**4.3 までは「押しても何も起きない」窓が
  開き、直前の記録が成功していると status 行に「記録しました。…」が残って失敗が成功のように
  見える**
- **4.2**: 突然変異テストで無関係な 7〜10 件が 1 秒のタイムアウトで落ちることがある。
  変異体では止まらなくなった送信や推定の action の Promise が未解決のまま残り、後続の
  テストの更新を止めるためである。**単独実行（`-t`）で分類しないと検知件数を読み誤る**
- **4.3**: 4.2 の申し送り 3 件のうち、**失敗の描画・記録の結果の居座り・`note` の代入は
  閉じた**。残る未検知は**反映時の上書き防止ガード（`entry.per100g !== null || entry.edited`）
  のみ**で、`edited` が立つ経路が無いため **4.4 の責務**である
- **4.3**: `operation`（`"record" | "estimate" | null`）を導入した。**`useActionState` の
  state は外から消せない**（dispatch 以外に更新手段が無い）ため、結果の領域が 1 つだと
  記録の成功が推定の失敗に居座る。領域を 2 つに分ける案は `role="status"` が 2 つになって
  読み上げが二重になり、居座りも解決しない
- **4.3**: 推定の成功時に「推定しました。」を出す。`operation` を導入すると、出さないと
  読み上げ領域が**空になる**（「推定中です。」の次が無音）
- **4.3**: **100g あたりの値は画面に描かないと受入基準 2.7 が満たせない**（レビューで
  指摘された）。hidden input の `value` にしか無い状態では、推定が 1 桁ずれた値を返しても
  換算後の数字からは見分けられない。design の Open Questions が「推定の品質が落ちても
  気づけない — 利用者が値を見て気づく」を唯一の安全弁としているため、根拠になる値を
  読み取り専用で出す。**4.4 で修正の入力欄に置き換わる**
- **4.3**: 行ごとの文面の検査は **`within` で `<li>` に限定する**。画面全体から探すと、
  理由を一覧の外に食材名なしで並べた変異体でも通る（レビュアーが実測）。あわせて
  **モックの `note` に食材名を含めない**（「肉」を含む文面だと、食材名が偶然入っている
  ことに頼った検査になる）
- **4.5 への申し送り**: 値が無い食材の行の文面が **4 系統**に分かれている。優先順は
  換算後の値 → 「100g あたりの値は 0 以上の数値で入力してください。」→
  「推定できませんでした。{note}」→「100g あたりの値がありません」。**4.5 で一律の印を
  入れるときに揃え方を決めること。** 既存テストが「100g あたりの値がありません」の
  **出現数を数えている**ため干渉する
- **4.5 への申し送り**: **欄を空にした食材は「推定する」で埋め直せない。** 推定の対象が
  「値が読めず、かつ利用者が直していない食材」なので、一度直した食材は空にしても対象に
  戻らない。手で入れ直すか取り消して加え直すしかなく、**「推定する」が無効になるだけで
  理由が画面に出ない**。4.5 で値が揃っていない食材を示すときに、この状態の説明も入れること
- **4.5 への申し送り**: 推定に失敗した食材に**片方の欄だけ入力すると `note` が消える**。
  優先順で「入力が不正」が「推定できませんでした。{note}」より先に来るため。
  受入基準 5.1（どの食材の推定ができなかったか）が一時的に見えなくなる。
  入力を始めた時点では理由の役目は済んでいるが、4.5 で文面を揃えるときに扱いを決めること
