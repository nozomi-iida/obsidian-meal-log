# Implementation Plan

- [ ] 1. 実測で設計の前提を潰す

`meal-record` では design を書き終えた時点で GitHub API を実際に叩き、「重複は 422（409 ではない）」を
確定させた。**実測しなければ「重複なのに権限エラーと表示する」実装になっていた。**

本 spec では `ANTHROPIC_API_KEY` が環境に無いため、この工程を design の段階で行えなかった。
**実装の最初に行う。**

  - **確認に使うスクリプトはリポジトリの外（scratchpad）に置く。** トークンはコマンドラインに渡さず
    `.env.local` から読む（`meal-record` の 2.1 で確立した手順）
  - **完了状態**: 結果が `research.md` に記録されている。**曖昧な名前で `null` が返らなかった場合は
    2.1 に進まず、design の見直しに戻る**（プロンプトの作り直し、または候補を複数出させて

## 補足

### 実測を先に置いた理由

`meal-record` では design を書き終えた時点で実測を済ませ、その結果（重複は 422）を design に
反映してから実装に入った。本 spec は `ANTHROPIC_API_KEY` が無いため同じ順序にできなかった。

**タスク 1.1 の結果によって design が変わりうる。** 曖昧な名前で `null` が返らない場合は、
プロンプトの作り直しか、別の仕掛け（候補を複数出させて食い違いを検知するなど）が必要になる。
**その判定を 1.1 の完了状態に入れてある。**

### 並列実行について

- **1.2 は 1.1 と並行して進められる**（どちらも実測で、互いの結果に依存しない）
- **4.1 は API キーを必要としない。** 画面から 100g あたりの入力欄を外す作業で、
  推定の配線は 4.2 以降である。1.x / 2.1 / 3.1 と並行して進められる
- それ以外は一直線に依存する。4.2 以降はすべて `record-form.tsx` を触るため同時に進めると衝突する

### 本 spec に含めないもの

- **推定した値の保存** — プリセットの spec が扱う。何を貯めるべきかは記録が溜まってから決める
- **外食・人が作ったものの記録** — 生で測れない。写真からの推定として後続の spec が扱う
- **食材名の正規化** — 入力された表記をそのまま記録に使う

### 本 spec の完了後に steering を直す

`.kiro/steering/tech.md` の「食材のデータの持ち方」が「記録のたびに利用者が名前と
100g あたりの値を入力する」と書いている。本 spec の完了でこれが古くなる。
`/kiro-steering` で拾う。

### `meal-record` から引き継ぐ知見

実装に入る前に `.kiro/specs/meal-record/tasks.md` の `## Implementation Notes` を読むこと。
とくに次の 5 件は本 spec でも同じ失敗が起きうる。

- **下書き行に項目名を付けない**（4.1）— 付けると送信全体が入力不正になる
- **日時の 0 埋めはテストで押さえる**（4.2）— 1 桁になる時刻でテストすること
- **`<form action={formAction}>` を使わない**（4.3）— React の自動リセットで `<select>` が壊れる
- **負の値と YAML の引用**（6.1）— 横断検証で見つかった。要件の文面に忠実な実装が意図から外れた例
- **`.env*` は Read / Write / Edit から触れない**（2.1）— `git diff` をファイル名なしで使う

## Implementation Notes

- **4.1**: 「記録する」の無効化は 4 条件（`pending` / `entries.length === 0` /
  `eatenAt === ""` / `hasMissingValue`）だが、**4.1 の時点で突然変異テストが検知できるのは
  `hasMissingValue` と `entries.length === 0` の 2 条件だけである**。`per100g` を埋める経路が
  まだ無く `hasMissingValue` が常にボタンを無効にするため、他の条件の寄与が観測できない。
  14 件の突然変異で確認した
- **4.1**: 値を持たない食材も **4 項目すべてを並べ、値の無い 2 項目を空文字で出す**。
  項目を省くと `parseFoodInputs` の長さ一致検査が崩れ、別の食材の値が隣にずれて入る。
  `name` ごと省くと**その食材が記録から静かに抜ける**（誤った記録が「成功」として作られる）。
  空で出せば受付の `parseNumber` が空文字を `null` と判定し、`headers()` も vault も触る前に
  送信全体が入力不正になる。**「記録する」の無効化が壊れても値の無い記録が vault に書かれない**
- **4.2 / 4.3 への申し送り**: `per100g` を埋められるようになった時点で、次の 2 件の
  アサーションを**回復すること**。
  1. **時刻が空のとき「記録する」が押せない**こと。この条件は design.md の Validation の
     列挙に一度抜けており、`meal-record` の 4.2 のレビューの申し送りだけで救われた。
     記録を残さずに無検査のまま引き継ぐと、同じ失敗を繰り返す
  2. **送信中は押せず、重ねての送信が受付に届かない**こと。`submit()` に `pending` の
     ガードは無く、**二重送信を止めているのは `disabled` 属性だけ**である
- **4.1**: 合計の算出（`calculateItem` → `sumNutrition`）の画面側の経路は 4.1 では到達できない。
  どの食材も値を持てないため合計が常に 0 になる。純粋関数は `nutrition.test.ts` が担保しており、
  画面側は 4.3 で戻る
