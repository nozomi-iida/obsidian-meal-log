# Requirements Document

## Project Description (Input)

### 誰が問題を抱えているか

利用者本人ひとり。このアプリの開発者でもある。体重 82kg、タンパク質の目標は 131〜180g/日。
厳密な栄養管理が目的ではなく、月末に「タンパク質が足りていたか」を数字で振り返れることが目的。

### 現状

`meal-record` で記録の経路は通った。スマホのホーム画面からアプリを開き、食材を入力して
送信すると vault に Markdown が 1 つ置かれる。

ただし**食材 1 件につき 3 項目を手で打つ**。名前・100g あたりのカロリー・100g あたりの
タンパク質である。100g あたりの値は利用者が自分で調べて入力する。

1 食に 3〜4 件の食材があるので、1 回の記録で 9〜12 個の数値を打つことになる。
`meal-record` の design.md はこれを「**入力の手間が初期リリースの最大の弱点**」と記録し、
「面倒で記録しなくなれば『精度より継続』の方針が崩れる」と自認している。

### 何が変わるべきか

**食材名と量の 2 つを入れれば、カロリーとタンパク質が出る状態にする。**

100g あたりの値は AI が推定する。利用者は自分で調べない。

これにより 1 件あたりの入力が 3 項目から 2 項目に減り、調べる手間がなくなる。

### 確認を取って決めたこと（2026-10-12）

`meal-record` の requirements が「後続の spec に送るもの」として挙げた未決定事項を、
利用者への確認で決めた。

| 論点 | 決定 | 理由 |
|---|---|---|
| 量をいつの状態で測るか | **調理前（生の状態）** | 下記のとおり、これが精度にいちばん効く |
| 食材名の指定の粒度 | **名前だけ。自由に書く** | 生が基準なので調理法の指定が不要になる。皮の有無などは名前に書けば AI が拾う |
| 推定の結果の示し方 | **1 つの値を出し、手で直せる** | 毎回選ばせるより、そのまま通すときの所作が 0 になる |
| 推定の根拠 | **出さない。値だけ示す** | 画面を簡潔に保つ。値が実感と違えば直せばよい |
| 推定を走らせる時機 | **「推定する」ボタンを別に置く** | 入力中に何度でも推定できる。記録は値が揃ってから |
| 推定できなかったとき | **その場で手入力に切り替える** | `meal-record` の入力欄が残っているので成立する。記録を諦めずに済む |
| 外食・人が作ったもの | **本 spec では扱わない** | 生で測れない。写真からの推定として後続の spec で扱う |

### 確認を取らずに決めたこと（後から変えられる）

次の 2 件は利用者の確認を取っていない。設計の構造には影響しないため、推奨のまま進めた。
**実際に使って違っていれば変更する。**

| 論点 | 決定 | 根拠 | 変えた場合の影響 |
|---|---|---|---|
| 推定した 100g あたりの値に小数を許すか | **許す**（受入基準 2.6） | 鶏もも皮つきのタンパク質は 16.6g。整数に丸めて 17 にすると 2.4% の誤差が出る。目標 150g に対して 3.6g | 整数にすると修正の入力欄が整数で済み、画面と検証が少し簡素になる |
| 推定の失敗の原因を区別するか | **区別する**（受入基準 5.6） | 通信が原因なら再送で直るが、食材名が原因なら何度送っても直らない。区別しないと利用者が無駄に再送する | 文面を 1 つにまとめれば画面は簡潔になる。ただし通信の失敗で「手入力してください」と出ると、再送すれば済むのに手で調べることになる |

#### 画面の流れ

「推定する」と「記録する」を別のボタンにする。

```
[食材を追加する欄]
  鶏もも  300g   [加える]

鶏もも 300g           [取り消す]
白米  200g           [取り消す]

  [ 推定する ]  ← 何度でも押せる
       ↓
鶏もも 300g  190/P16.6  → 570 / P50
白米  200g  156/P2.5   → 312 / P5
                 計  882 kcal / P56

  [ 記録する ]  ← 値が揃っていないと押せない
```

**推定は 100g あたりの値を持たない食材だけを対象とする。** 利用者が手で直した値は
再推定で上書きしない（受入基準 3.4）。食材を足して推定し直しても、既に直した値は残る。
`meal-record` の「利用者が選んだ食事区分を時刻の変更で上書きしない」と同じ考え方である。

#### 推定の精度をどう確かめるか

AI の出力は毎回変わりうるため「鶏もも → P16.6」という形の自動テストは置かない。
**実測で一度確かめる**。`meal-record` で GitHub API の応答を実測して前提を潰したのと
同じ工程である。

- 代表的な食材を 10 件ほど選び、文部科学省の食品成分データベースの値と比べる
- 幅（±20% 程度）に入るかを見る
- 結果を research.md に記録する
- 推定の呼び出しをモックして、結果の扱い（修正・失敗・合計）はテストで守る

#### 推定のコスト

Claude Haiku 4.5 の価格（$1/MTok 入力、$5/MTok 出力）で見積もると、
1 回の推定（食材 4 件）は入力 300 トークン・出力 150 トークン程度で約 $0.001。

```
1 日 4 食   →  $0.004
月 120 回   →  $0.13（約 20 円）
```

**「毎回推定する」方針はコストの観点では問題にならない。** 残る論点は待ち時間だけである。

#### 「調理前（生）」を基準にした理由

調理法より「いつ測るか」の方が精度に効く。

```
生 100g あたり（文部科学省 食品成分データベース由来）
  鶏もも 皮つき   P16.6 / 190kcal
  鶏もも 皮なし   P19.0
  鶏むね 皮つき   P21.3 / 133kcal
  鶏むね 皮なし   P23.3
```

皮の有無でタンパク質が 14% 違う。ただしそれより大きいのが調理による水分の減少である。

```
生の鶏もも 100g を焼くと約 70g になる

生 100g      P16.6
焼き 70g     P16.6   同じ肉。重さだけ減った
焼き 100g    P23.7   1.4 倍
```

**皿を見て「250g くらい」と記録し、そこに生の値を当てると、タンパク質を 3 割低く見積もる。**
利用者の目標は 131〜180g/日 なので、150g 食べたつもりが 100g だったという規模の誤差になる。
裏の表示を見て生で測るなら、この誤差は生じない。

### 本 spec に持ち込まないもの（方針として引き継ぐ）

- **推定した値を貯めない。** `meal-record` の「アプリは何も覚えない」を引き継ぐ。
  同じ食材名でも記録のたびに推定する。貯める仕組みはプリセットの spec で扱う

### 後続の spec に送るもの

- **写真からの推定** — 外食と人が作ったものを記録できるようにする。生で測れないため、
  本 spec の「調理前の重量」という前提が成り立たない。**利用者が次にやりたいこととして
  挙げている**
- **プリセット**（よく食べるものを貯めて選ぶ）— 貯める仕組みは別の関心事。
  何を貯めるべきかは記録が溜まってから決める
- **献立単位の記録**（「鍋」のように複数の食材をまとめた単位）
- **食材名の正規化** — 入力された表記をそのまま記録に使う方針を引き継ぐ

## Introduction

食材名から 100g あたりのカロリーとタンパク質を推定し、利用者が自分で調べて入力する手間を
なくす機能を提供する。

利用者が入力するのは**食材の名前と量の 2 つ**になる。100g あたりの値は「推定する」を
押したときに推定する。推定した値は画面に示され、実感と違えば手で直せる。直した値は
推定し直しても上書きされない。記録は値が揃ってから行う。

量は**調理前（生の状態）**を基準とする。この前提のもとで推定する。

推定できなかった食材は、その食材だけ 100g あたりの値を手で入力して記録できる。
`meal-record` の入力の形が残っているため、推定に頼れないときも記録を諦めずに済む。

**推定した値は貯めない。** 同じ食材名でも記録のたびに推定する。

## Boundary Context

- **In scope**: 食材名からの 100g あたりの値の推定、推定した値の提示と修正、
  推定の失敗時の手入力への切り替え、推定中であることの提示
- **Out of scope**: 推定した値の保存と再利用、プリセットの登録と選択、
  献立単位の記録、写真からの推定、調理後の重量からの推定、食材名の正規化、
  推定の根拠の提示、複数の候補の提示
- **Adjacent expectations**:
  - 記録の形（frontmatter 8 項目、ファイル名の規則、本文の内訳）は `meal-record` が
    定めたものを変更しない。推定した値は 100g あたりの値として同じ経路に流す
  - カロリーとタンパク質を**食材ごとに整数へ丸め、合計はその和とする**規則を変更しない
  - 書き込みは常に新規作成であり、既存ファイルの読み取りと統合を行わない
  - 公開 URL の保護は `app-foundation` の遮断点が担う。本 spec は認証方式を定義しない
  - 量は利用者が調理前に測った値として扱う。外食のように生で測れない場合は
    本 spec の対象外であり、後続の spec が扱う

## Requirements

### Requirement 1: 食材の入力

**Objective:** As a 利用者, I want 食材の名前と量だけを入力したい,
so that 100g あたりの値を自分で調べなくて済む

#### Acceptance Criteria

1. When 記録画面を開いたとき, the Meal Log アプリ shall 食材の名前と食べた量を入力する手段を示す
2. The Meal Log アプリ shall 100g あたりのカロリーとタンパク質の入力を求めない
3. When 入力した食材を加えたとき, the Meal Log アプリ shall その食材を記録の対象に加える
4. If 食材名が空のまま加えられようとしたとき, then the Meal Log アプリ shall 対象に加えず、
   名前が必要であることを示す
5. If 量に数値として解釈できない値または 0 未満の値が入力されたとき, then the Meal Log アプリ
   shall 対象に加えず、入力が不正であることを示す
6. The Meal Log アプリ shall 1 回の記録に複数の食材を含められる
7. When 記録の対象に加えた食材を取り消したとき, the Meal Log アプリ shall その食材を対象から外す

### Requirement 2: 栄養価の推定

**Objective:** As a 利用者, I want 食材名から 100g あたりの値を自動で出してほしい,
so that 栄養成分を調べる手間がなくなる

#### Acceptance Criteria

1. When 記録の対象に食材があるとき, the Meal Log アプリ shall 推定を求める手段を示す
2. When 利用者が推定を求めたとき, the Meal Log アプリ shall 100g あたりの値を持たない
   食材について 100g あたりのカロリーとタンパク質を推定する
3. The Meal Log アプリ shall 推定を何度でも求められる
4. The Meal Log アプリ shall 推定を**調理前の状態**の 100g あたりの値として行う
5. The Meal Log アプリ shall 利用者が入力した食材名をそのまま推定の手がかりとして用いる
6. The Meal Log アプリ shall 推定した 100g あたりの値に小数を含められる
7. When 推定が終わったとき, the Meal Log アプリ shall 食材ごとの 100g あたりの値、
   食材ごとのカロリーとタンパク質、合計カロリーと合計タンパク質を示す
8. The Meal Log アプリ shall 推定の根拠を示さない
9. The Meal Log アプリ shall 食材 1 件に対して 1 組の値を示し、複数の候補を示さない

### Requirement 3: 推定した値の修正

**Objective:** As a 利用者, I want 推定された値が実感と違うときに直したい,
so that 納得できる数字で記録できる

#### Acceptance Criteria

1. When 推定した値が示されたとき, the Meal Log アプリ shall 食材ごとに
   100g あたりのカロリーとタンパク質を修正する手段を示す
2. When 利用者が 100g あたりの値を修正したとき, the Meal Log アプリ shall
   その食材のカロリーとタンパク質を修正後の値に応じて算出し直す
3. When 利用者が 100g あたりの値を修正したとき, the Meal Log アプリ shall
   合計カロリーと合計タンパク質を算出し直す
4. When 利用者が 100g あたりの値を修正したあとで推定を求めたとき, the Meal Log アプリ shall
   **修正した値を推定で上書きしない**
5. If 修正した値が数値として解釈できない値または 0 未満の値であるとき, then the Meal Log アプリ
   shall 記録を受け付けず、入力が不正であることを示す
6. The Meal Log アプリ shall 修正した値を記録に用いる

### Requirement 4: 推定中の提示と記録の受け付け

**Objective:** As a 利用者, I want 推定を待っている間それが分かり、値が揃うまで記録されないようにしたい,
so that 反応が無いのか待てばよいのかを判断でき、値の無い記録を作らずに済む

#### Acceptance Criteria

1. While 推定しているとき, the Meal Log アプリ shall 推定していることを示す
2. While 推定しているとき, the Meal Log アプリ shall 重ねての推定を受け付けない
3. While 推定しているとき, the Meal Log アプリ shall 記録を受け付けない
4. While 記録の対象が 1 件も無いとき, the Meal Log アプリ shall 推定と記録のいずれも
   受け付けない
5. While 100g あたりの値を持たない食材があるとき, the Meal Log アプリ shall 記録を受け付けない
6. While 100g あたりの値を持たない食材があるとき, the Meal Log アプリ shall
   **どの食材の値が揃っていないか**を示す

### Requirement 5: 推定できなかったときの扱い

**Objective:** As a 利用者, I want 推定できない食材があっても記録を続けたい,
so that 外出先で記録を諦めずに済む

#### Acceptance Criteria

1. If いずれかの食材の推定ができなかったとき, then the Meal Log アプリ shall
   **どの食材の推定ができなかったか**を示す
2. If いずれかの食材の推定ができなかったとき, then the Meal Log アプリ shall
   その食材について 100g あたりのカロリーとタンパク質を手で入力する手段を示す
3. When 手で入力した値で記録を求めたとき, the Meal Log アプリ shall その値を用いて記録する
4. If 推定ができなかったとき, then the Meal Log アプリ shall 入力した内容を保持し、
   やり直せる状態にする
5. If 一部の食材の推定だけができなかったとき, then the Meal Log アプリ shall
   **推定できた食材の値を保持する**
6. If 推定ができなかったとき, then the Meal Log アプリ shall 原因が通信によるものか
   食材名によるものかを示す

### Requirement 6: 推定した値の扱い

**Objective:** As a 利用者, I want アプリが食材のデータを溜め込まない状態を保ちたい,
so that 何を貯めるべきかが分かってから貯める仕組みを設計できる

#### Acceptance Criteria

1. The Meal Log アプリ shall 推定した 100g あたりの値を記録の完了後に保持しない
2. When 同じ食材名で再び記録したとき, the Meal Log アプリ shall 改めて推定する
3. The Meal Log アプリ shall 推定に用いる資格情報をソースコードおよびリポジトリに含めない
4. The Meal Log アプリ shall 推定に用いる資格情報を利用者の端末に渡さない
5. If 推定に用いる資格情報が設定されていないとき, then the Meal Log アプリ shall 推定を試みず、
   設定が不足していることを示す
