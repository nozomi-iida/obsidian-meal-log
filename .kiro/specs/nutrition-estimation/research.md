# Research & Design Decisions

## Summary

- **Feature**: `nutrition-estimation`
- **Discovery Scope**: Extension（既存の記録経路に推定を挟む）+ 外部 API の新規統合
- **Key Findings**:
  - **`fetch` だけで呼べる。** `@anthropic-ai/sdk` は不要で、`vault.ts` と同じ「`fetch` + ステータスコードで分類」の形にできる。`meal-record` と `app-foundation` の design が定めた「実行時依存は追加しない」を守れる
  - **構造化出力（`output_config.format`）が GA で、文法制約サンプリングによりスキーマ違反が原理的に出ない。** `kcal` / `protein` を nullable にすることで「**分からない**」を構造的に合法な出力にできる。これが「黙って嘘の値を返す」ことへの最強の防御になる
  - **`content[0]` を読んではいけない。** Haiku 5.5 はアダプティブ思考が既定 ON で、`content` の先頭に `thinking` ブロックが入りうる
  - **拒否は HTTP 200 で返る。** `stop_reason: "refusal"` を見ないと `content` が空のまま進む
  - **スキーマで数値の下限（`minimum`）と配列の件数（`minItems` は 0/1 のみ）を縛れない。** 非負の検証と件数の突き合わせはアプリ側に残る
  - **コストは論点にならない。** Haiku 5.5 は 10 万トークン以下なら $0.10/$0.50 per MTok。1 回約 $0.00034（0.05 円）、月 120 回で 6 円程度
  - **Vercel Hobby のタイムアウトは 300 秒。** 以前知られていた 10 秒 / 60 秒ではない。切られる心配はないが、ハングを利用者に待たせないため自前のタイムアウトが要る
- **Measured Findings**（タスク 1.1 / 1.2 の実測。詳細は「実測の結果」の節）:
  - **曖昧な名前で `null` が返る（ゲート PASS）。** 「肉」「野菜」「惣菜」「おかず」「飲み物」の 5 件 × 5 回すべてで `kcal` と `protein` が `null` になり、`note` に理由が 1 行で入った。**平均値を黙って返す挙動は一度も観測されなかった。** design の見直しは不要
  - **`content` の先頭に `thinking` ブロックが実際に入った。** 既定の 13 回のうち 7 回。**入るかどうかは要求ごとに変わる**ため、`content[0]` を読む実装は間欠的に壊れる。`thinking` フィールドは空文字（`display` の既定が `"omitted"`）だが**ブロックは来る**
  - **`stop_reason` は 27 回すべて `end_turn`。** 曖昧な名前で `refusal` にはならなかった
  - **たんぱく質の誤差は小さいが、エネルギーに穴が 1 つある。** 推定できた 8 件のうち 6 件が誤差 0%。ただし**鶏むねが 3 回のうち 2 回で +43.6%**（191 kcal / 成分表 133 kcal）。曖昧な名前には `null` を返すのに、**皮の有無で値が 1.5 倍変わる具体的な名前には自信が無くても数値を返す**
  - **`effort: "low"` + 思考 OFF は採らない。** 食材 4 件で 0.3 秒しか速くならず、鶏むねが 3 回とも成分表 -18.8% に固定され、豆腐まで `null` になる
  - **実時間は食材 4 件で 2.1〜2.9 秒、10 件で 4.6〜4.9 秒、30 件で 12.1 秒。** ばらつきの正体は思考が走るかどうかで、同じ入力でも 0.7 秒の差が出る
  - **暫定値はすべて据え置いた。** `AbortSignal.timeout` 30 秒 / `maxDuration` 60 秒 / `effort` は送らない / `max_tokens` 8192

## Research Log

### Messages API を `fetch` で呼ぶ

- **Context**: `meal-record` と `app-foundation` の design が「実行時依存は追加しない。`dependencies` は `next` / `react` / `react-dom` のみ」と定めている。SDK を入れずに済むかを確かめる
- **Sources Consulted**: [Messages API](https://platform.claude.com/docs/en/api/messages), [Versioning](https://platform.claude.com/docs/en/api/versioning), [Errors](https://platform.claude.com/docs/en/api/errors)
- **Findings**:
  - エンドポイントは `POST https://api.anthropic.com/v1/messages`
  - 必須ヘッダは `x-api-key` / `anthropic-version` / `content-type: application/json`
  - **`anthropic-version` に指定すべき値は `2023-06-01`。** 存在する値は `2023-06-01` と `2023-01-01`（初期リリース、deprecated）の 2 つだけで、日付を上げる必要はない
  - API リファレンスのヘッダ表は `anthropic-version` を optional と書いているが、versioning のページは "you must send an `anthropic-version` request header" と書いている。**記述が食い違っているので常に送る**
  - 必須のボディは `model` / `max_tokens` / `messages` の 3 つ
  - **`temperature` / `top_p` / `top_k` は送ってはいけない。** Haiku 5.5 では既定値以外を送ると 400
- **Implications**:
  - `src/lib/vault.ts` と同じ構造で書ける。新しい依存を入れない
  - API バージョンはヘッダで明示する。送らないと将来の既定変更で挙動が変わりうる（`vault.ts` で `X-GitHub-Api-Version` を明示したのと同じ理由）

### 応答から文字列を取り出す経路の罠

- **Context**: `content` の配列から推定結果の JSON を取り出す
- **Findings**:
  - **Haiku 5.5 はアダプティブ思考が既定で ON**、`display` の既定値は `"omitted"`
  - そのため `content` の先頭に **text が空の `thinking` ブロックが入りうる**
  - `content[0].text` を読むと空文字になる
- **Implications**:
  - **必ず型で絞り込む**: `content.find((b) => b.type === "text")?.text`
  - 思考トークンは `max_tokens` を消費する。これがレイテンシの主因になる

### エラーの分類

- **Sources Consulted**: [Errors](https://platform.claude.com/docs/en/api/errors)
- **Findings**:

  | 分類 | 検出方法 |
  |---|---|
  | 認証の失敗 | `401` `authentication_error`（キーが不正・revoke 済み・期限切れ） |
  | 課金の問題 | `402` `billing_error` |
  | 権限の不足 | `403` `permission_error` |
  | リクエストの不正 | `400` `invalid_request_error` / `413` `request_too_large` |
  | レート制限 | `429` `rate_limit_error` |
  | 通信の失敗 | `fetch` の throw / `500` `api_error` / `504` `timeout_error` / `529` `overloaded_error` |

  - **401 / 402 / 403 は意味が違う。** `vault.ts` は GitHub API 向けに 401/403 をまとめて `permission` にしているが、Claude API では 401 = キー自体が無効、402 = 課金の問題、403 = キーにリソース権限がない
  - **拒否は HTTP 200 で返る。** `stop_reason: "refusal"` + `stop_details.category`。Haiku 5.5 には server-side fallback がないので再送しても普通はまた拒否される
  - **`stop_reason: "max_tokens"` なら JSON が途中で切れている**
  - 429 には通常 `retry-after` が付くが、月次上限に当たった 429 には付かず再試行しても回復しない
- **Implications**:
  - **ステータスコードだけでは足りない。** `content` を読む前に `stop_reason` を見る
  - 残高切れを「キーが無効」と表示すると原因が分からなくなるため、少なくとも 401 / 402 / 403 は分ける

### 構造化された出力

- **Context**: 食材が複数あるので 1 回の呼び出しで複数の値を返させたい。パースが壊れない形を選ぶ
- **Sources Consulted**: [Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)
- **Findings**:
  - **`response_format` というパラメータは存在しない。** 相当する機能の正式名は `output_config.format`
  - `output_format`（トップレベル）は deprecated。新規コードでは使わない
  - **GA、beta ヘッダ不要。`claude-haiku-5-5` は対応モデルに明記されている**
  - 仕組みは **grammar-constrained sampling**（文法制約サンプリング）。トークンのサンプリング自体をスキーマに合う出力だけに制限するため、**スキーマに合わない JSON が出てくることが原理的にない**
  - 結果は `tool_use` ではなく **`text` ブロック**に JSON 文字列として入る

  | 方法 | スキーマ適合の保証 | 評価 |
  |---|---|---|
  | `output_config.format` | **あり**（文法制約） | **最も壊れにくい** |
  | Tool use + `strict: true` | あり（同じ文法エンジン） | 用途は「関数の引数を型安全にする」こと。JSON が欲しいだけなら遠回り |
  | プロンプトで JSON を要求 → `JSON.parse` | **なし** | 前置き文や ```json フェンスが混ざる。最も脆い |

  - 公式も両者を住み分けている: 構造化出力は「最終応答の形式」、strict tool use は「ツール名と入力パラメータ」
- **スキーマの制約（設計に影響する）**:
  - オブジェクトの `additionalProperties` は **`false` 必須**
  - **数値の制約（`minimum` / `maximum` / `multipleOf`）が未対応** → `kcal >= 0` をスキーマで縛れない
  - **配列の `minItems` は 0 か 1 のみ**（`maxItems` なし）→ 「必ず 3 件返せ」を縛れない
  - 文字列の制約（`minLength` / `maxLength`）が未対応
  - 使えるもの: `enum` / `const` / `anyOf` / `allOf` / 内部 `$ref` / `$defs` / `default` / `required` / 文字列 `format`
  - 上限: 任意プロパティ 24 個、`anyOf` を使うプロパティは 16 個まで
- **Implications**:
  - **`kcal` / `protein` を `anyOf: [number, null]` にする。** これが「分からないと言わせる」仕掛けそのものである
  - **非負の検証と件数の突き合わせはアプリ側に残る。** スキーマで縛れない部分がそこに全部来る
  - トップレベルを配列にできるかは公式に記述がないため、`{ items: [...] }` のオブジェクトで包む
  - スキーマは文法にコンパイルされ最終使用から 24 時間キャッシュされる。構造を変えるとキャッシュ無効
  - Haiku 5.5 のプロンプトキャッシュ最小長は 512 トークン。短いシステムプロンプトでは効かないので期待しない

### パースの失敗をどう扱うか

- **Findings**: 文法制約があるので「スキーマに合わない JSON」は来ないが、**途中で切れた JSON は来る**。公式が挙げる 2 つの経路は `stop_reason: "max_tokens"` と `stop_reason: "refusal"`
- **Implications**: 次の順で確かめる
  1. `stop_reason` を見る（`end_turn` 以外は失敗として扱う）
  2. `content` から `type === "text"` を取り出す（なければ失敗）
  3. `JSON.parse` を try/catch で囲む
  4. **パース後も必ずアプリ側で検証する** — 件数が入力と一致するか、値が有限の非負数か
  5. どこかで失敗したら「推定できなかった」として扱い、**ゼロや適当な値で埋めない**

### モデルの選択

- **Sources Consulted**: [Models overview](https://platform.claude.com/docs/en/models/overview), [Haiku 5.5 overview](https://platform.claude.com/docs/en/models/haiku-5-5/overview), [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- **Findings**:

  | モデル | ID | 価格 $/MTok（入力 / 出力） | 相対レイテンシ |
  |---|---|---|---|
  | Claude Fable 5.1 | `claude-fable-5-1` | 10 / 50 | Slower |
  | Claude Opus 5.5 | `claude-opus-5-5` | 4 / 20 | Moderate |
  | Claude Sonnet 5.5 | `claude-sonnet-5-5` | 2 / 10 | Fast |
  | **Claude Haiku 5.5** | **`claude-haiku-5-5`** | **0.10 / 0.50** | **Fastest** |

  - **Haiku 5.5 だけプロンプト長で価格が変わる**: 10 万トークン以下なら $0.10 / $0.50、超えると $0.50 / $2.50。本 spec は数百トークンなので常に安いほう
  - ID に日付サフィックスは付かない（`claude-haiku-5-5-20261007` のような文字列は存在しない）
  - 公式の Haiku 5.5 の位置づけが用途に一致する: "high-volume, latency-sensitive tasks such as **classification, extraction**, and routing"
  - effort の既定は `medium`。`thinking: {"type": "disabled"}` を受け付けるが **effort が `low` / `medium` / `high` のときだけ**（`xhigh` / `max` との併用は 400）
- **コストの見積もり**:
  ```
  システムプロンプト 400 トークン + 食材名 30 トークン ≈ 入力 430
  出力（思考込み）600

  1 回        約 $0.00034（0.05 円）
  月 120 回   約 $0.04（6 円）
  ```
- **Implications**:
  - **コストは選択の決め手にならない。** Sonnet 5.5 でも 1 回 1 円程度
  - **決め手は精度。** Haiku 5.5 で足りるかは実測で確かめる
  - 速度を上げるには `effort: "low"` + 思考 OFF。ただし公式は「思考を切るとユーザーに見えるテキストに推論っぽい文章が混ざる挙動が増える」と明記している

### 推定の精度を上げる書き方

- **Sources Consulted**: [Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations), [Prompting Claude Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)
- **Findings**:
  - 公式が挙げる幻覚対策のうち本 spec で使えるのは **"Allow Claude to say 'I don't know'"** と **"External knowledge restriction"** の 2 つ。残り 2 つ（直接引用による grounding、引用による検証）は参照文書がないため使えない
  - **`note` に「段階的な理由」を要求してはいけない。** スキーマのフィールドで step-by-step の推論を要求すると `reasoning_extraction` カテゴリの **refusal** を引き起こしうる。公式は「短い説明（short explanation）を求めるにとどめる」と指示している
  - 思考 OFF / `low` effort では推論っぽいテキストが可視テキストに混ざりやすい。公式の対処は「アダプティブ思考 + `medium` effort に切り替える」
- **Implications**:
  - `note` は 1 行の短い説明にとどめ、推論の過程を書かせない
  - **プロンプトだけに頼らず、スキーマで「分からない」の置き場所を作る**ことが要点である

### タイムアウト

- **Sources Consulted**: [Vercel function duration](https://vercel.com/docs/functions/configuring-functions/duration), `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/maxDuration.md`
- **Findings**:

  | プラン | 既定 | 最大 |
  |---|---|---|
  | **Hobby** | **300s** | **300s** |
  | Pro | 300s | 800s |

  - **無料プランで 300 秒使える。** 以前知られていた 10 秒 / 60 秒はもう当てはまらない
  - Server Action は専用の上限を持たず、**それが属するページの `maxDuration`** に従う。Next.js 公式: "If using Server Actions, set the `maxDuration` at the **page level**"
- **Implications**:
  - **Vercel に切られる心配は実質ない。** 300 秒に対して Haiku 5.5 の 1 リクエストは桁違いに短い
  - 本当のリスクは「ハングしたリクエストを利用者が待たされる」こと。**`fetch` に `signal: AbortSignal.timeout(...)` を付ける**。abort も `fetch` が throw するので既存の try/catch に乗る
  - ストリーミングは不要（出力が数百トークンで、JSON を全部揃えてからパースする）

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| SDK を入れる | `@anthropic-ai/sdk` を `dependencies` に追加 | 型が付く。エラーがクラスで分類される | **先行する 2 つの spec が定めた「実行時依存は追加しない」を破る。** バンドルが増える | 採らない |
| **採用**: `fetch` + 純粋関数 | `src/lib/estimate.ts` が `fetch` で呼び、プロンプトの組み立てと応答の検証を分ける | `vault.ts` と同じ構造。依存が増えない。検証を単体テストできる | 型を自分で書く | `vault.ts` の実績に揃える |
| プロンプトで JSON を要求 | 構造化出力を使わず `JSON.parse` | 実装が短い | **スキーマ適合の保証がない。** 前置き文やフェンスが混ざる | 採らない |
| Tool use + `strict: true` | 関数呼び出しの形で JSON を得る | 保証は構造化出力と同等 | 用途が違う。`tool_choice` の強制が使えないモデルもある | 採らない |

## Design Decisions

### Decision: 推定を純粋な検証と HTTP の呼び出しに分ける

- **Context**: 推定の結果は「スキーマに合っているか」とは別に「件数が合っているか」「非負か」をアプリ側で確かめる必要がある（スキーマで縛れない）
- **Selected Approach**: `src/lib/estimate.ts` に HTTP の呼び出しを置き、応答の検証（件数・非負・null の扱い）を**引数を取る純粋関数**として分ける
- **Rationale**: 検証の部分が単体テストで確かめられる。`vault.ts` が検証を持たないのに対し、推定は検証が本体になるため分ける価値が大きい
- **Trade-offs**: ファイルが 1 つ増える
- **Follow-up**: 外部 API を呼ぶ部分は実測で担保する（`vault.ts` と同じ）

### Decision: 「分からない」をスキーマで合法にする

- **Context**: 黙って嘘の値を返されるのが最悪の失敗である
- **Selected Approach**: `kcal` / `protein` を `anyOf: [number, null]` にし、`note` を必須にする
- **Rationale**: 構造化出力は文法制約なので、`null` を合法にしておけば**モデルが数値を出すしかない状況を作らずに済む**。プロンプトだけの指示より強い
- **Trade-offs**: `null` が返ったときの画面の分岐が必要になる（受入基準 5.1 / 5.2 で既に求めている）
- **Follow-up**: 「肉」のような曖昧な名前で実際に `null` が返るかは**実測が必要**

## Risks & Mitigations

- **曖昧な食材名で黙って平均値を返す可能性** — 「分からせる」仕組みは用意できるが、Haiku 5.5 が実際に素直に `null` を返すかは**ドキュメントからは判断できない**。**これが本 spec でいちばん重要な未検証事項である**。実測で確かめる
- **日本語の食材名での精度が不明** — 公式に日本食品標準成分表との一致度に関する情報はない。代表的な食材を成分表の値と比べて誤差を測る
- **`content[0]` を読む実装を書いてしまう** — 思考ブロックが先頭に入るため空文字になる。`find` で型を絞る。テストで押さえる
- **拒否（HTTP 200）を成功として扱ってしまう** — `stop_reason` を見ないと `content` が空のまま進む。テストで押さえる
- **推定の品質が落ちても気づけない** — AI の出力は毎回変わるため自動テストにできない。利用者が値を見て気づくことになる。これは受け入れた制約である
- **API キーの期限切れ** — 401 として扱い、何をすればよいか分かるようにする

## 実測が必要な前提（タスク 1.1 / 1.2 で潰す）

`meal-record` で GitHub API の応答を実測して「重複は 422（409 ではない）」を確定させたのと同じ工程である。
**API キーが環境に無いため設計の段階で実施できなかった。** タスク 1.1 と 1.2 で行う。
**1.1 の結果によって design が変わりうる。**

| 確かめること | なぜ必要か |
|---|---|
| **「肉」「野菜」のような曖昧な名前で `null` が返るか** | 黙って平均値を返されるのが最悪の失敗。プロンプトとスキーマの仕掛けが実際に効くかは実測しないと分からない |
| 食材 4 件の推定にかかる実時間 | 公式は相対順位（Fastest / Fast）しか公開していない。待ち時間の設計に必要 |
| 代表的な食材 10 件の誤差 | 日本食品標準成分表の値と比べ、幅（±20% 程度）に入るか |

| `stop_reason` が `end_turn` 以外になる条件 | 拒否と `max_tokens` の扱いを決めるため |

## 実測の結果（タスク 1.1 / 1.2）

### 測り方

`src/lib/estimate.ts` の `estimate` を**そのまま呼んだ**。実装と違う呼び方をすると、
測ったものが実装の挙動と一致しない。生の応答（`stop_reason` / `content` の `type` の列 /
`usage`）を観測するために `globalThis.fetch` を包み、応答を素通しさせつつ選んだ
フィールドだけを記録した。

`effort` と思考の比較は、**実装が組んだ要求ボディを土台に書き換える**形で行った。
ボディを別に組み直すと比較が実装からずれる。

- 資格情報は `.env.local` をスクリプトの中で読んだ。コマンドラインには渡していない
- 応答をそのままログに出していない（要求のヘッダに API キーが含まれる）
- 呼び出し回数は計 27 回、概算費用は $0.006（約 1 円）
- モデルは `claude-haiku-5-5`、要求のボディは実装のまま（`temperature` 等は送らない）

### 1.1 曖昧な名前で `null` が返るか — **返る（ゲート PASS）**

**スキーマで `kcal` / `protein` を nullable にし、プロンプトで「推測で数値を埋めては
ならない」と指示する仕掛けは実際に効いた。** 5 件 × 5 回（既定 2 回 + `effort: "low"` +
思考 OFF 3 回）のすべてで両方が `null` になり、`note` に理由が 1 行で入った。
**平均値を黙って返す挙動は一度も観測されなかった。**

| 入力 | `kcal` | `protein` | `note`（既定での実測） |
|---|---|---|---|
| 肉 | `null` | `null` | 種類が特定できないため推定不可 |
| 野菜 | `null` | `null` | 種類が特定できないため推定不可 |
| 惣菜 | `null` | `null` | 内容が特定できないため推定不可 |
| おかず | `null` | `null` | 内容が特定できないため推定不可 |
| 飲み物 | `null` | `null` | 種類が特定できないため推定不可 |

**曖昧な名前と具体的な名前を混ぜても食材ごとに判定が分かれた。**
`["肉", "鶏もも", "野菜", "ブロッコリー"]` で「肉」「野菜」が `null`、
「鶏もも」が 200/16.6、「ブロッコリー」が 33/4.3。
**1 件が `null` でも他の食材の値が失われない**という設計（個別の失敗と全体の失敗を分ける）が
実際の応答でも成り立っている。

### 1.1 `content` の先頭に `thinking` ブロックが入るか — **入る**

**`content[0]` を読む実装は壊れていた。** 実測した既定の 13 回のうち **7 回**で
`content` が `["thinking", "text"]` になり、`thinking` ブロックが先頭に来た。

```
content の type の列（既定、食材 10 件 × 3 回）   ["thinking","text"] ["thinking","text"] ["thinking","text"]
content の type の列（既定、食材 4 件 × 5 回）    ["text"] ["text"] ["text"] ["thinking","text"] ["thinking","text"]
content の type の列（既定、曖昧 5 件 × 2 回）    ["text"] ["text"]
```

**入るかどうかは要求ごとに変わる（アダプティブ思考なので一定ではない）。** これが
いちばん危ない性質である。`content[0].text` を読む実装は**同じ入力でも通るときと
通らないときがある**ため、テストが通ってしまい本番で間欠的に `malformed` になる。
`content.find((b) => b.type === "text")` で型を絞る実装（2.1）が正しい。

`thinking` ブロックの `thinking` フィールドは**空文字だった**。Haiku 5.5 の
`thinking.display` の既定が `"omitted"` であるため。**中身が空でもブロックは来る**ので、
`text` の有無で絞らないと `undefined` を読むことになる。

### 1.1 `stop_reason`

**観測したのは `end_turn` のみ（27 回すべて）。** `stop_details` は常に `null`。
曖昧な名前でも `refusal` にならなかった。`max_tokens` も観測していない（下記の通り
出力が上限から遠い）。

`stop_reason` を `content` より先に見る実装（2.1）は、実測では一度も発火しない経路である。
**発火しないことを「不要」と読み替えてはいけない**。拒否は HTTP 200 で返るため、
発火したときに `content` を読むと壊れた値が通る。

### 1.2 実時間

|---|---|---|---|---|---|
| 食材 4 件・既定 | 5 | 2433 | 2143 | 2862 | 2152 / 2147 / 2143 / 2862 / 2859 |
| 食材 4 件・`low` + 思考 OFF | 5 | 2129 | 2067 | 2233 | 2067 / 2183 / 2233 / 2069 / 2094 |
| 食材 10 件・既定 | 3 | 4801 | 4632 | 4908 | 4632 / 4862 / 4908 |
| 食材 10 件・`low` + 思考 OFF | 3 | 3271 | 3050 | 3676 | 3676 / 3086 / 3050 |
| 曖昧 5 件・既定 | 2 | 1850 | 1810 | 1889 | 1889 / 1810 |
| 食材 20 件・既定 | 1 | 4320 | — | — | 4320 |
| 食材 30 件・既定 | 1 | 12121 | — | — | 12121 |

**ばらつきの正体は思考が走るかどうかである。** 食材 4 件・既定の 5 回は
2.14 秒が 3 回（思考トークン 0）と 2.86 秒が 2 回（思考トークン 197 / 178）に
きれいに割れた。**同じ入力でも 0.7 秒の差が出る**ので、平均だけ見て上限を決めてはいけない。

**最も遅かったのは食材 30 件の 12.1 秒**（思考トークン 1695）。記録に含める食材の
件数に上限は無いので、ここが実質的な最悪値の目安になる。

### 1.2 トークンの使用量

| 条件 | `input_tokens` | `output_tokens` | うち思考 |
|---|---|---|---|
| 食材 4 件・既定（思考なしの回） | 861 | 177〜199 | 0 |
| 食材 4 件・既定（思考ありの回） | 861 | 385〜401 | 178〜197 |
| 食材 10 件・既定 | 896 | 888〜972 | 472〜551 |
| 食材 10 件・`low` + 思考 OFF | 895 | 470〜513 | 0 |
| 食材 20 件・既定 | 944 | 852 | 0 |
| 食材 30 件・既定 | 1000 | 2830 | 1695 |

**思考トークンは出力トークンの約半分を占める。** 食材 10 件の既定で 888 のうち 472、
30 件で 2830 のうち 1695。`usage.output_tokens_details.thinking_tokens` に出る。

**`max_tokens = 8192` は妥当だが余裕は無限ではない。** 30 件で 2830 なので、
1 件あたり約 94 トークン（思考込み）。線形に伸びるとすると **8192 に当たるのは
80〜90 件あたり**である。1 回の食事で 80 件を入れることは現実的に無いので、
この値は据え置いてよい。**上限に当たるとその回の推定が食材ごと全部失われる**ため、
下げる理由も無い（`max_tokens` は上限であって課金される値ではない）。

入力トークンはシステムプロンプトとスキーマが大半で、食材が 4 件でも 30 件でも
861〜1000 の範囲に収まる。1 回の費用は食材 4 件の既定で約 $0.00022（0.03 円）。

### 1.2 `effort: "low"` + 思考 OFF と既定（`medium` + 思考 ON）の比較

要求は受け付けられた（200）。Haiku 5.5 は **`effort` が `high` 以下のときだけ
`thinking: {"type": "disabled"}` を受け付ける**ので、`low` との組み合わせは通る。

| 見るもの | 既定（`medium` + 思考 ON） | `low` + 思考 OFF | 判定 |
|---|---|---|---|
| 食材 4 件の実時間 | 平均 2433ms | 平均 2129ms | **差は 0.3 秒**。採る価値が無い |
| 食材 10 件の実時間 | 平均 4801ms | 平均 3271ms | 1.5 秒速い |
| 出力トークン（10 件） | 888〜972 | 470〜513 | 約半分 |
| ばらつき | 大きい（思考が走る回とそうでない回で 0.7 秒差） | 小さい（2067〜2233ms） | `low` のほうが読みやすい |
| **曖昧な名前の `null`** | 5/5 件すべて `null` | 5/5 件すべて `null` | **どちらも効く** |
| **`note` に推論が流れ込むか** | 流れ込まない | **流れ込まない。** ただし文面がやや長くなる（「種類（牛・豚・鶏など）が不明なため推定できない。」） | 実害は無い |
| 具体的な食材の `null` | 2/10 件（プロテイン・シリアル） | **3/10 件（プロテイン・シリアル・豆腐）** | `low` は余計に諦める |
| 鶏むねの値 | 191/19.5、191/19.2、145/21.3 | **108/22.3（3 回とも）** | **`low` は成分表から大きく外れる** |

**`low` + 思考 OFF を採らない。** 判断の決め手は 2 つである。

1. **鶏むねの値が成分表から外れる。** 成分表（皮つき・生）は 133 kcal / P21.3 g。
   `low` + 思考 OFF は 3 回とも **108 kcal / P22.3 g** を返した。これは
   **皮なしの値に近い**。プロンプトは「皮の有無が書かれていない場合は皮つきを仮定し、
   その仮定を note に 1 行で書く」と指示しているのに、`low` ではこの指示が効いていない。
   既定では 191/19.5 など別の外れ方をするが、**思考を切ると誤りが 3 回とも同じ値に
   固定される**。ばらつきが消えることは精度の改善ではない
2. **`low` は余計に `null` を返す。** 「豆腐」を 3 回とも `null` にした（既定は
   3 回とも 72/6.6）。**安全側に外れるので記録が静かに狂うことは無い**が、
   利用者が手で入力する回数が増える。受入基準 4.6（値が揃っていない食材を示す）の
   負担が増えるだけで、得るものは 0.3 秒である

**速度の差は待ち時間の設計を変えない。** 食材 4 件で 2.4 秒と 2.1 秒はどちらも
「待てる」範囲であり、`AbortSignal.timeout` も `maxDuration` もこの差では動かない。

### 1.2 代表的な食材 10 件の誤差

成分表の値は**文部科学省が公開している公式 Excel（日本食品標準成分表（八訂）
増補2023年・第2章 本表）から引いた**。推定値は既定の設定で 3 回測った。

- Excel: <https://www.mext.go.jp/content/20260327-mxt_kagsei-mext-000029402_02.xlsx>
- 掲載ページ: <https://www.mext.go.jp/a_menu/syokuhinseibun/mext_00001.html>
- 検索できる公式 DB: <https://fooddb.mext.go.jp/>

たんぱく質は成分表に 2 種類ある（「アミノ酸組成によるたんぱく質」と「たんぱく質・
基準窒素による」）。下表は慣例的な「たんぱく質」である**基準窒素による値**を基準にした。

| 食材 | 推定 kcal（3 回） | 成分表 kcal | 誤差 | 推定 P（3 回） | 成分表 P | 誤差 |
|---|---|---|---|---|---|---|
| 鶏もも（11221 皮つき生） | 200 / 204 / 204 | 190 | +5.3〜+7.4% | 16.6 / 16.6 / 16.6 | 16.6 | **0%** |
| 鶏むね（11219 皮つき生） | 191 / 191 / **145** | 133 | **+43.6% / +43.6% / +9.0%** | 19.5 / 19.2 / 21.3 | 21.3 | -8.5〜0% |
| 白米（01083 精白米うるち米・生） | 358 / 356 / 358 | 342 | +4.1〜+4.7% | 6.1 / 6.1 / 6.1 | 6.1 | **0%** |
| 納豆（04046 糸引き納豆） | 200 / 200 / 200 | 184 | +8.7% | 16.5 / 16.5 / 16.5 | 16.5 | **0%** |
| 卵（12004 全卵生） | 151 / 151 / 151 | 142 | +6.3% | 12.3 / 12.3 / 12.3 | 12.2 | +0.8% |
| バナナ（07107 生） | 86 / 86 / 86 | 93 | -7.5% | 1.1 / 1.1 / 1.1 | 1.1 | **0%** |
| プロテイン（成分表に収載なし） | **`null` × 3** | 381（市販品） | — | **`null` × 3** | 75（市販品） | — |
| シリアル（01137 コーンフレーク） | **`null` × 3** | 380 | — | **`null` × 3** | 7.8 | — |
| 豆腐（04032 木綿豆腐） | 72 / 72 / 72 | 73 | -1.4% | 6.6 / 6.6 / 6.6 | 7.0 | -5.7% |
| ブロッコリー（06263 花序生） | 33 / 33 / 33 | 37 | -10.8% | 4.3 / 4.3 / 4.3 | 5.4 | **-20.4%** |

プロテインの成分表上の収載は無い（「ホエイ」「乳清」「たんぱく質濃縮」で本表を
全件検索して不在を確認した）。比較の相手はメーカーが 100g あたりで公表している値
（マイプロテイン Impact ホエイプロテイン ノンフレーバー 381 kcal / P75 g,
<https://www.myprotein.jp/sports-nutrition/impact-whey-protein/10530943.html>）。
**成分表に無いものを `null` で返したのは正しい挙動である。**

#### 読み取れること

**1. たんぱく質の精度は高い。** 推定できた 8 件のうち **6 件が誤差 0%**、
最大でも -20.4%（ブロッコリー）。本アプリの目的はたんぱく質の管理なので、
ここが一致するのは都合がよい。ブロッコリーの -20.4% も、成分表のもう一方の値
（アミノ酸組成による 3.8 g）と比べれば +13.2% に収まる。**成分表が 2 種類の値を
持つことが、そのまま誤差の下限になっている。**

**2. エネルギーには系統的な偏りがある。** 鶏もも・白米・納豆・卵が +4〜+9% 高く、
バナナ・ブロッコリーが -8〜-11% 低い。**八訂はエネルギーの算出方法そのものを
変えており、文部科学省自身が「以前のエネルギー量と単純には比較できない」と
説明している。** 推定値は八訂より前の版の値に一致している可能性が高いが、
前の版の原典は引いていないので**確認していない**。
いずれにせよ**偏りは ±10% の内側**で、幅（±20%）には収まる。

**3. ±20% に収まらなかったのは鶏むねの 1 件だけ。だが、これが最も重い結果である。**
3 回のうち **2 回が 191 kcal（+43.6%）**、1 回が 145 kcal（+9.0%）。
`effort: "low"` + 思考 OFF では 3 回とも 108 kcal（-18.8%）。
**同じ食材名で 108・145・191 と 1.8 倍の幅がある。**
原因は皮の有無の扱いと推測できる（成分表の皮なしむねは皮つきより低い）。
プロンプトは「皮の有無が書かれていない場合は皮つきを仮定する」と指示しているが、
**鶏むねでは効いていない。** 一方で鶏ももは 3 回とも皮つきの値を返している。

**この 1 件が受入基準 3.x（推定した値を利用者が修正できる）の根拠になる。**
±20% に収まらない値が黙って通る経路が実在するので、**修正の手段は「あると便利」
ではなく必須である。** また 4.4（修正した値を再推定で上書きしない）も、
再推定で 191 → 145 と値が動くことが実測できたため必要性が裏づけられた。

### 1.2 で決めたこと

| 項目 | 暫定値 | **決めた値** | 根拠 |
|---|---|---|---|
| `AbortSignal.timeout`（`estimate.ts`） | 30 秒 | **30 秒（据え置き）** | 実測の最大は食材 30 件の **12.1 秒**。食材 4 件で 2.9 秒、10 件で 4.9 秒。30 秒は最悪値の **2.5 倍**の余裕がある。これより短くすると件数の多い記録で正常な応答を打ち切る。長くしてもハングを待たせるだけで利得が無い |
| `maxDuration`（`page.tsx`） | 60 秒 | **60 秒（据え置き）** | 推定側の上限（30 秒）を下回らない受け皿として機能する。実測の最悪値 12.1 秒に対し 5 倍の余裕。配置先の既定 300 秒を使う理由は無い |
| `effort` と思考の設定 | 既定（`medium` + 思考 ON） | **既定（据え置き）。`effort` と `thinking` は送らない** | `low` + 思考 OFF は食材 4 件で 0.3 秒しか速くならず、**鶏むねが 3 回とも 108 kcal（成分表から -18.8%）に固定され**、豆腐まで `null` になる。0.3 秒と引き換えに精度を落とす取引になる |
| `max_tokens` | 8192 | **8192（据え置き）** | 食材 30 件で出力 2830（うち思考 1695）。1 件あたり約 94 トークンなので 8192 に当たるのは 80〜90 件あたり。1 回の食事でその件数には達しない |

**`estimate.ts` と `page.tsx` のコードは 1.1 / 1.2 では変更していない。** 上記は
すべて「暫定値のまま据え置く」という結論なので、**コメントから「実測で裏づけていない
暫定値である」の記述を外す作業だけが残る。** 別のタスクとして扱う。
`page.tsx` のコメントが `estimate.ts` の値（30 秒）を参照しているので、
**片方だけ直すと記述が静かに古くなる。両方を同時に直すこと。**

### 1.1 / 1.2 で design に戻さなかった理由

タスク 1.1 の完了状態は「曖昧な名前で `null` が返らなかった場合は 2.1 に進まず
design の見直しに戻る」であった。**`null` は返ったので design の見直しは不要である。**
プロンプトの作り直しも、候補を複数出させて食い違いを検知する仕掛けも要らない。

ただし**鶏むねの +43.6% は仕掛けの穴である。** 曖昧な名前には `null` を返すが、
**「鶏むね」のように具体的でありながら皮の有無で値が 1.5 倍変わる名前には、
自信が無くても数値を返す。** 「分からないと言わせる」仕掛けは
「名前が特定できないか」で働いており、「値の幅が大きいか」では働いていない。
**本 spec では修正の手段（3.x / 4.4）でこれを受け止める。**
プリセットの spec（推定した値の保存）が、利用者が一度直した値を再利用する形で
本質的な解決になる。

## 実測の結果（タスク 1.3 プロンプトの調整）

### 測り方

1.2 と同じ測り方にした（`harness.mjs` 経由で `src/lib/estimate.ts` の `estimate` を
そのまま呼ぶ）。**システムプロンプトだけを `patchBody` で差し替えて、変更前と候補を
同じ実行の中で測った。** ファイルを書き換えながら測ると、変更前の条件を同じ条件で
測り直せず、モデル側の時間帯による変動が前後の比較に混ざる。

**変更前（A）の文面が当時の `SYSTEM_PROMPT` とバイト単位で一致することを照合してから
測った**（`cmp-a2.mjs`）。再構成した文面がずれていると前後の比較が成立しない。

- 呼び出し回数は計 73 回、概算費用は $0.02（約 3 円）
- 成分表の値と `effort` の設定は 1.2 と同じ。たんぱく質は**基準窒素による値**で比較した
- 最後に、確定した `estimate.ts` を `patchBody` なしで 7 回呼んで、
  **実際に残したコードが測ったとおりに振る舞うことを確かめた**

### 原因は皮の有無ではなく「拠った成分表の版」だった

タスクの前提は「皮の有無の指示が鶏むねに効いていない」であった。**これは誤りだった。**
1.2 の推定値を八訂と並べると、**8 件すべてが八訂ではなく七訂（2015年版）の値に
一致している。**

| 食材 | 推定値（変更前） | 八訂 | 七訂 |
|---|---|---|---|
| 白米 | 358 | 342 | 358 |
| 納豆 | 200 | 184 | 200 |
| 卵 | 151 | 142 | 151 |
| バナナ | 86 | 93 | 86 |
| 豆腐 | 72 | 73 | 72 |
| ブロッコリー | 33 | 37 | 33 |
| 鶏もも | 204 | 190 | 204 |
| 鶏むね | 145 | 133 | 145 |

**1.2 が「系統的な偏り」と呼んだ +4〜+9% は、八訂のエネルギー算出方法の変更そのもの
である。** 文部科学省が「これまでの方法で算出したエネルギー値との比較ができなくなる」と
説明しているとおりで、推定値が古い版に一致していたという 1.2 の推測は当たっていた。

**鶏むねの 191 kcal / P19.5 は、七訂よりさらに古い版の値である。** 鶏むねは
七訂（145）と、それより古い版（191）の間で振れていた。**皮の有無ではない**
（皮なしの八訂は 105 kcal で、191 はどちらの皮の状態からも外れている）。

七訂の原典（2015年版の Excel）は引いていないので、上の表の七訂の列は**一次資料で
確認していない**。ただし大阪市の資料が精白米 80g で 285 → 274 kcal（100g 換算で
約 356 → 343）という変化を示しており、推定値 358 が八訂より前の値であることと整合する。
**決め手は下の A/B であって、版の同定そのものではない。**

- <https://www.city.osaka.lg.jp/kodomo/cmsfiles/contents/0000309/309034/verup2020tebiki.pdf>

### 前後の数字

食材 8 件 × 各回、成分表は八訂、たんぱく質は基準窒素による値。

| 候補 | 回数 | 鶏むね kcal の分布 | 鶏むねの ±20% 超え | kcal 平均誤差 | kcal の ±20% 超え | P 平均誤差 | 曖昧 5 件が全部 `null` |
|---|---|---|---|---|---|---|---|
| **A（変更前）** | 21 | 108×1 / **145×12** / **191×8** | **8/21** | 8.6% | 9/168 | 4.2% | 7/7 回 |
| B | 3 | 145×2 / 191×1 | 1/3 | 8.1% | 1/24 | 3.5% | 2/2 回 |
| C | 3 | **145×3** | 0/3 | 6.5% | 0/24 | 3.4% | 2/2 回 |

**鶏むねは D で完全に安定した。** 25 回すべて 145 kcal（+9.0%）/ P21.3（0%）。
変更前は 21 回中 8 回が 191 kcal（+43.6%）で、**±20% の幅を 38% の確率で外していた**。

**B だけでは効かない。** 特定の食材名を一般則に書き換えても 3 回中 1 回は 191 に振れた。
**効いたのは版を指定する 1 行（C / D）である。** タスクが立てた仮説（例として挙げた
「鶏もも」が特定の食材への指示として読まれている）は、**それ自体では原因ではなかった。**

**ただし版の指定は「八訂に揃える」ところまでは効いていない。** 白米 358・納豆 200・
卵 151・バナナ 86・ブロッコリー 33 は D でも七訂相当のまま返る。
**効いたのは「さらに古い版に振れるのを止める」ところである。** +4〜+9% の系統的な
偏りは残っており、これはプロンプトでは動かなかった。

### 1.3 で決めたこと

**候補 D を残した（VERDICT: IMPROVED）。** `SYSTEM_PROMPT` の変更点は 2 つ。

1. 「鶏もも」を例に挙げた 1 行を、**特定の食材名を出さない一般則**に書き換えた
   （部位・皮の有無・脂身の有無）。単体では効かなかったが、害も無く、
   タスクが求めた「食材全般に効く書き方」になる
2. **拠る版（日本食品標準成分表2020年版（八訂））を指定する 1 行を足した。**
   これが鶏むねの外れ値を消した本体である

「調理前（生）の状態」の前提と「推測で数値を埋めてはならない」の指示は**変えていない**。
`note` に段階的な推論も要求していない（1 行の仮定を書かせるだけ）。

あわせて、1.1 / 1.2 で裏づけが取れた値から**「実測で裏づけていない暫定値である」の
記述を外した**。`estimate.ts` の `TIMEOUT_MS` / `MAX_TOKENS` / `effort` と
`page.tsx` の `maxDuration`。**値そのものは変えていない。** `page.tsx` のコメントは
`estimate.ts` の 30 秒を参照しているので、両方を同時に直した。

**残った課題**: +4〜+9% の系統的な偏り（推定値が八訂より前の版に寄る）は
プロンプトでは動かなかった。たんぱく質の精度は高い（平均 3.4%）ので、
**たんぱく質の管理という目的には足りている。** カロリーの偏りは
修正の手段（3.x / 4.4）とプリセットの spec で受け止める。

### 1.3 追測: 食材 30 件の実時間（n=1 → n=3）

`TIMEOUT_MS` の根拠が 1 サンプルしか無かったため測り直した。
**確定した `estimate.ts` をそのまま呼んだ**（`patchBody` なし）。食材のプールは
1.2 の `t12-scale.mjs` と同じ 30 件で、件数だけでなく中身も揃えてある。

| 回 | 実時間 | 出力トークン | うち思考 | `stop_reason` | 推定できた件数 |
|---|---|---|---|---|---|
| 1 | 15.8 秒 | 3315 | 2036 | `end_turn` | 25/30 |
| 2 | **17.2 秒** | 3756 | 2504 | `end_turn` | 25/30 |
| 3 | 15.5 秒 | 3437 | 2201 | `end_turn` | 24/30 |

**平均 16.2 秒、最大 17.2 秒、幅は 1.7 秒。** ばらつきは小さい（30 件では
3 回とも思考が走るので、4 件のときのような「走る回と走らない回」の二極化が無い）。

**1.2 の n=1 の 12.1 秒は楽観的な値だった。** 3 回の最小（15.5 秒）すら
12.1 秒を 3.4 秒上回る。**1 サンプルで最悪値を決めてはいけない**という
一般的な教訓がそのまま出た形である。

#### `TIMEOUT_MS = 30_000` は据え置くが、余裕は想定より薄い

| | 1.2 の記述（n=1） | 実測（n=3） |
|---|---|---|
| 食材 30 件の最大 | 12.1 秒 | **17.2 秒** |
| `TIMEOUT_MS` 30 秒の余裕 | 2.5 倍 | **1.7 倍** |
| `maxDuration` 60 秒の余裕 | 5 倍 | **3.5 倍** |

**20 秒を超える回は無かったので値は変えていない。** コメントの根拠を
n=3 の数字に差し替えた（`estimate.ts` と `page.tsx` の両方）。

**ただし余裕が 2.5 倍から 1.7 倍に下がったことは記録しておく価値がある。**
記録に含める食材の件数に上限は無いので、**30 件を大きく超える記録では
`TIMEOUT_MS` に当たりうる。** 件数と実時間の関係は線形ではない（20 件は
思考が走らず 4.3 秒だった一方、30 件は 3 回とも思考が走って 15〜17 秒）ため、
**何件で 30 秒に達するかは測っていない。**

#### `MAX_TOKENS` の根拠も同じ n=1 に乗っていた（未修正）

同じ測定で**出力トークンも 1.2 の記録を上回った**。

| | 1.2 の記述（n=1） | 実測（n=3） |
|---|---|---|
| 食材 30 件の出力トークン | 2830（うち思考 1695） | **3315〜3756**（うち思考 2036〜2504） |
| 1 件あたり | 約 94 トークン | **約 110〜125 トークン** |
| `MAX_TOKENS = 8192` に当たる件数 | 80〜90 件 | **65〜74 件** |

**`estimate.ts` の `MAX_TOKENS` のコメントは「1 件あたり約 94 トークンなので
当たるのは 80〜90 件あたり」と書いており、この数字は実測とずれている。**
このタスクで触ってよいのは `TIMEOUT_MS` のコメントだけだったため
**修正していない。** 値（8192）そのものは、65〜74 件でも 1 回の食事では
達しないので据え置きで妥当である。**コメントの数字を直すかは別途の判断が要る。**
