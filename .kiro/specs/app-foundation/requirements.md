# Requirements Document

## Project Description (Input)

### 誰が問題を抱えているか

利用者本人ひとり。このアプリの開発者でもある。

### 現状

プロジェクトは `create-next-app` 直後の状態で、`src/app/` にテンプレートの
ページが1枚あるだけ。以下がいずれも未整備:

- Lint / フォーマッタが入っていない
- テストフレームワークが入っていない
- デプロイしても URL を知る者なら誰でも開ける
- スマホのホーム画面から起動できない

この状態のまま機能実装に入ると、後から Biome を入れた時点で既存ファイル全体に
整形差分が走る。また cc-sdd の `/kiro-impl` は TDD（RED → GREEN）で実装し
タスクごとにレビュアーが検証する作りのため、テスト基盤がないと各タスクの
完了判定が「動いたように見える」だけになり、自律実装の品質保証が丸ごと外れる。

さらに、この先の記録機能は GitHub のアクセストークンをサーバー側に置いて
vault に commit する。認証がないまま公開すると、URL を知った第三者が
vault にファイルを作れてしまう。認証は機能実装の前に必要。

### 何が変わるべきか

**機能はまだ持たないが、デプロイして本人だけが開けるアプリの土台**を完成させる。

- Biome で Lint とフォーマットが走る（ESLint / Prettier は使わない）
- Vitest でテストが実行でき、`/kiro-impl` の TDD モードが機能する
- middleware による Basic 認証で、パスワードを知る者だけが開ける
- PWA としてスマホのホーム画面に追加でき、そこから起動できる

この spec の完了時点で、記録機能（`meal-record`）の実装に着手できる状態になる。

## Introduction

`create-next-app` 直後の状態から、機能実装に着手できる土台を整える。
コード品質の検査、自動テストの実行、アクセス制御、ホーム画面への追加の 4 領域を揃える。

食事の記録そのもの（プリセットの選択、vault への書き込み）は本 spec に含まない。
それらは後続の `meal-record` が担う。本 spec は「まだ何もしないが、
安全に公開でき、テストを書きながら開発を進められるアプリ」を完成させる。

## Boundary Context

- **In scope**: コード品質の検査と整形、自動テストの実行、アクセス制御、
  ホーム画面への追加と起動
- **Out of scope**: 食事の記録機能、vault への書き込み、プリセットの提供、
  写真からの推定、公開環境への配置作業、オフラインでの記録、アイコンの意匠
- **Adjacent expectations**: アクセス制御は公開環境で第三者を遮断するために設けるが、
  公開環境への配置そのものは本 spec の作業対象ではない。
  アイコンの意匠は別タスクで用意するため、本 spec は暫定のアイコンで成立させる。
  ホーム画面への追加と起動の実機確認は利用者が別途行うものとし、本 spec の完了は
  **アプリが手元の環境で起動し、4 領域が検証できる状態**をもって判断する。

## Requirements

### Requirement 1: コード品質の検査と整形

**Objective:** As a 開発者, I want 静的解析と整形を 1 つのコマンドで実行したい,
so that レビュー時に書式の差分がノイズにならず、実装の中身だけを見られる

#### Acceptance Criteria

1. When 検査コマンドが実行されたとき, the 開発環境 shall プロジェクト内の対象ファイル全体を検査し、規約違反の一覧を出力する
2. If 規約違反が存在するとき, then the 開発環境 shall 違反ごとにファイルパスと行番号を示す
3. If 規約違反が存在するとき, then the 開発環境 shall 非ゼロの終了コードで終了する
4. When 整形コマンドが実行されたとき, the 開発環境 shall 自動修正が可能な違反を修正し、修正した件数を報告する
5. The 開発環境 shall 既存ファイルを含むプロジェクト全体を検査の対象とする

### Requirement 2: 自動テストの実行

**Objective:** As a 開発者, I want テストをコマンド 1 つで実行したい,
so that 実装タスクごとに、失敗するテストを書いてから実装に進める

#### Acceptance Criteria

1. When テスト実行コマンドが実行されたとき, the 開発環境 shall 全テストを実行し、成功数と失敗数を報告する
2. If いずれかのテストが失敗したとき, then the 開発環境 shall 失敗したテストの名称、期待した値、実際の値を出力する
3. If いずれかのテストが失敗したとき, then the 開発環境 shall 非ゼロの終了コードで終了する
4. While 監視モードで起動しているとき, the 開発環境 shall ファイルの変更を検知して関連するテストを再実行する
5. The 開発環境 shall テストが 1 件も存在しない状態でも異常終了せず、実行件数 0 として報告する

### Requirement 3: アクセス制御

**Objective:** As a 利用者, I want 認証情報を知る自分だけがアプリを開ける状態にしたい,
so that 第三者に vault への書き込み経路を渡さずに済む

#### Acceptance Criteria

1. When 認証情報を伴わない要求が届いたとき, the Meal Log アプリ shall 認証を要求し、ページの内容を返さない
2. When 正しい認証情報を伴う要求が届いたとき, the Meal Log アプリ shall 要求されたページを返す
3. If 誤った認証情報が提示されたとき, then the Meal Log アプリ shall 再度認証を要求する
4. The Meal Log アプリ shall すべての画面と、外部から到達できるすべての経路を認証の対象とする
5. The Meal Log アプリ shall 認証情報をソースコードおよびリポジトリに含めない

### Requirement 4: ホーム画面への追加と起動

**Objective:** As a 利用者, I want スマホのホーム画面からアプリを起動したい,
so that 食事のたびにブラウザを開いて URL を辿る手間をなくせる

#### Acceptance Criteria

1. When 対応するブラウザでアプリを開いたとき, the Meal Log アプリ shall ホーム画面への追加に必要な情報（名称、アイコン、起動時の表示方法）を提供する
2. When ホーム画面から起動されたとき, the Meal Log アプリ shall ブラウザのアドレスバーを伴わない表示で起動する
3. The Meal Log アプリ shall ホーム画面および起動中のアプリ一覧において、指定された名称とアイコンで表示される
