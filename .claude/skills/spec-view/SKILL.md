# spec-view Skill

## 役割

Markdown の設計ドキュメントを読み、**レビューで見るべき箇所だけが目に入る HTML ビュー**を生成する。

md は 300〜500 行になり、確定事項と判断待ちが同じ見た目で並ぶため、
どこに注目すればよいかが分からなくなる。このスキルはその軽重を可視化する。

**正本は常に md。** このスキルが作る HTML は生成物であり、`.kiro/_view/` に置かれ gitignore される。
内容を直すときは md 側を編集し、このスキルを再実行する。HTML を直接編集しない。

---

## 実行手順

### 1. 対象を特定する

引数から対象の md を解決する。

| 引数 | 対象 |
|---|---|
| `product` / `tech` / `structure` | `.kiro/steering/{引数}.md` |
| `{feature} requirements\|design\|tasks` | `.kiro/specs/{feature}/{種別}.md` |
| パスそのもの | そのファイル |
| 引数なし | `.kiro/steering/*.md` と `.kiro/specs/*/*.md` を Glob で列挙し、AskUserQuestion で選ばせる |

### 2. 読む

- 対象の md を読む
- steering（`product.md` / `tech.md` / `structure.md`）も読む。矛盾の検出に使う
- spec の場合は同じ feature の `requirements.md` / `design.md` も読む。整合性の確認に使う

### 3. 要確認を判定する

以下に当てはまる記述を抽出する。**最大 5 件**。多いと絞る意味がなくなるため、
超える場合は影響の大きいものを選ぶ。

| # | 分類 | 見つけ方 |
|---|---|---|
| 1 | **根拠が示されていない主張** | なぜそうするかが書かれていない決定 |
| 2 | **将来の予測に依存する決定** | 「後で〜するから今は〜しておく」の形 |
| 3 | **外部への依存** | 別のファイル・システム・既存運用と歩調を合わせる必要がある箇所 |
| 4 | **明示的な未決定** | 「未定」「TBD」「要検討」「どちらか」 |
| 5 | **矛盾** | 同一ドキュメント内、または steering や他の spec と食い違う記述 |

**会話の文脈がある場合**（このセッションで自分が書いた md など）は、
**「指示されていないのに自分で決めた箇所」を最優先で挙げる。**
書いた本人にしか分からず、最も見落とされやすいため。

#### 各件に必ず書くもの

- **見出し** — 何が問題かを一文で言い切る
- **説明** — どういう記述で、なぜ判断が要るのか
- **影響** — 「誤っていた場合どうなるか」／未決定なら「決めないと何が進まないか」

**影響は必須。** これがないと読み手は判断できず、カードがただの指摘リストになる。

### 4. HTML を組む

`template.html`（このスキルのディレクトリ）を読み、以下を守る。

**そのまま引き継ぐもの**（1文字も変えない）
- `<title>` 以降のフォント `<link>` と `<style>` ブロック全体
- `<title>` の中身だけドキュメント名に差し替える

**必ず入れる4つ**

| 要素 | 内容 |
|---|---|
| `.masthead` | ドキュメント名、一行要約、正本のパス、規模、読了目安 |
| `.tiles` | 件数（確定 / 要確認 / 未決定）。0 件のタイルには `zero` を足して色を落とす |
| `.verdict` | 「何件読めば済むか」を一文で。要確認 0 件なら「判断が必要な箇所はありません」 |
| `footer` | 正本の md パスと「ここは生成物」の明示 |

**`.alerts`** は要確認カード。**0 件なら丸ごと省略する**（空の見出しを残さない）。
未決定のカードには `.alert.is-open` を使い、藍色にする。

**判断の記録欄** — 要確認カードが 1 枚でもあるなら、以下を必ず行う。

1. 各 `.alert` に `data-decision="01"` を付ける（値はカード番号と一致させる）
2. 各カードの末尾に `template.html` の `.decide` ブロックをそのまま入れる（中身の書き換え不要）
3. `template.html` 末尾の `<script>` を 1 文字も変えずにコピーし、`DOCKEY` だけ差し替える
   - steering なら `product` / `tech` / `structure`
   - spec なら `{feature}-{種別}`（例: `meal-record-design`）
4. publish 時に `capabilities: {db: {}}` を渡す

ページを再生成しても、`DOCKEY` とカード番号が同じなら記録された判断は復元される。
**したがってカード番号は実行のたびに変えない。** 指摘が消えた場合、その番号は欠番にする。

**本文**は元ドキュメントの構造に合わせて自由に組んでよい。
`template.html` のコンポーネント見本（`.sec` / `.flow` / `.tasks` / `table` / `pre` / `.oos`）から
適したものを選ぶ。見本のコメントは出力に含めない。

- 要確認に該当するセクションには `data-origin="claude"`、未決定には `data-origin="open"` を付ける（左レールが色付く）
- スコープ外や優先度の低い塊は `.oos` で視覚的に落とす
- 本文中の該当箇所に `← 要確認 01` のような参照を添え、冒頭のカードと結びつける

### 5. 書き出して公開する

**出力先**

| 元ファイル | 出力 |
|---|---|
| `.kiro/steering/product.md` | `.kiro/_view/product.html` |
| `.kiro/specs/{feature}/design.md` | `.kiro/_view/{feature}-design.html` |

`.kiro/_view/` が `.gitignore` に入っていなければ追加する。

**公開**

1. `.kiro/_view/` に HTML を書く
2. Artifact として publish する
   - **要確認が 1 件以上あるなら `capabilities: {db: {}}` を渡す**（判断の記録欄が動くようになる）
   - 同じファイルパスで再実行すると同じ URL が更新される
   - `favicon` は初回のみ指定する。再実行時は省略して既存のアイコンを保つ
3. URL と、要確認の件数・各件の見出しをユーザーに提示する

## 記録された判断を読む

ユーザーがページ上で判断を記録したら、Artifact ツールでストアを読む。

```
action: "read_db"
url: <そのビューの artifact url>
db_op: "query"
collection: "decisions"
query: { where: [["doc", "eq", "<DOCKEY>"]] }
```

各文書の中身:

| フィールド | 値 |
|---|---|
| `no` | カード番号（`01` など） |
| `title` | カードの見出し |
| `status` | `decided`（決めた） / `deferred`（保留） / `dismissed`（指摘は不要） |
| `note` | 判断の内容（自由記述） |
| `updatedAt` | ISO 8601 |

読んだあとの扱い:

- `decided` → **md に反映する**。ただし書き換える前にユーザーに内容を確認する
- `dismissed` → その指摘は誤りだったということ。md は変えない。
  同じ指摘を次回また挙げないよう、判定の根拠を見直す
- `deferred` → 次回のビューでも要確認として残す

---

## 出力の形

チャットには以下だけを返す。HTML の中身は貼らない。

```
{ドキュメント名} のビュー

URL: {artifact url}

確定 {n} / 要確認 {n} / 未決定 {n}

要確認:
1. {見出し}
2. {見出し}
```

---

## 禁止事項

- **md を書き換えない。** このスキルは読み取りと HTML 生成のみ。
  レビューの結果 md を直す必要が出た場合は、ユーザーに確認してから別途行う
- **CSS を変更しない。** 見た目が実行ごとにブレるとレビューの信頼性が落ちる。
  デザインを変えたい場合は `template.html` を編集する
- **要確認を水増ししない。** 該当がなければ 0 件でよい。
  0 件は「レビュー済みで問題なし」という有効な結論であり、失敗ではない
